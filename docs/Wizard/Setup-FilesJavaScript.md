# Setup: files that JavaScript reads

Your .NET app writes the files, and JavaScript or TypeScript opens them: a web page the user drops an export on, a Node.js script, an Electron tool.

## In short

| | .NET (writes) | JavaScript (reads) |
|---|---|---|
| Package | `LtMsgPack` | `@lsmsgpack/client` (npm) |
| Settings | the defaults + `SchemaVersion = SchemaVersion.Described` | `new Decoder()` |
| TypeScript classes (optional) | | generated by `lsmsgpack-ts` (NuGet tool `LsMsgPack.TypeScript`) |

```
dotnet add package LtMsgPack
npm install @lsmsgpack/client
```

## The .NET side

```csharp
using LsMsgPack;
using LtMsgPack;

LtMsgPackSerializer serializer = new LtMsgPackSerializer(new LtMsgPackOptions
{
  SchemaVersion = SchemaVersion.Described // the schema also says the type of each property
});

await File.WriteAllBytesAsync("export.drawing", serializer.Serialize(drawing));
```

**Why `SchemaVersion.Described`?** The file starts with a schema that lists the property names of each class. To keep files small, values that are `0`, `false` or `null` are left out (written as an empty slot). Your .NET classes know what that empty slot means for each property; JavaScript has no classes, so it can't tell whether a missing `count` should be `0` or `null`. The *described* schema adds the type of every property (`int`, `string`, `datetime`, a list of `Line`...), so JavaScript gets complete objects. It adds roughly 5 to 10 bytes per property to the schema, once per file. Your .NET app reads both versions, so turning it on doesn't affect existing files.

## The JavaScript side, without generated classes

```ts
import { Decoder } from '@lsmsgpack/client';

const decoder = new Decoder(); // one decoder reads any number of files

// in a browser, from <input type="file"> or drag and drop
const bytes = new Uint8Array(await file.arrayBuffer());
// in Node.js: const bytes = await readFile('export.drawing');

const drawing = decoder.decode(bytes).value as Drawing;
console.log(drawing.title, drawing.shapes.length);

// Your own description of the data (or skip it and use the objects untyped)
interface Drawing { title: string | null; created: Date; shapes: Shape[]; }
```

- Property names are **camelCase**, as ASP.NET Core writes JSON: `Title` becomes `title`. Pass `new Decoder({ propertyNames: 'dotnet' })` to keep `Title`.
- Every property is there, also the ones left out of the file: `0`, `false`, `null`, or the `[DefaultValue]` of the property.
- A `Circle` in a `List<IShape>` arrives as an object with its own properties and `$type: 'Circle'`, so `switch (shape.$type)` tells them apart.
- `DateTime` becomes a `Date`, `Guid` a string, `decimal` a number (or text: `new Decoder({ decimal: 'string' })`), `byte[]` a `Uint8Array`. The full list: [TypeScriptClient.md](../TypeScriptClient.md#values).

## With generated TypeScript classes (recommended for TypeScript projects)

`lsmsgpack-ts` reads your compiled .NET classes and writes matching TypeScript classes, including the initial values your constructors set:

```bash
dotnet tool install -g LsMsgPack.TypeScript

dotnet build MyApp.Models -c Release
lsmsgpack-ts --assembly MyApp.Models/bin/Release/net8.0/MyApp.Models.dll --root Drawing --no-schemas --out web/src/models.ts
```

- `--root Drawing` is the class the file holds (add `--root` once per kind of file). Everything it reaches (`Shape`, `Circle`, `Square`...) is included.
- `--no-schemas` skips the schema set, which is only for HTTP: a file carries its own schema.
- Keeping the classes in their own class library (`MyApp.Models`) makes this easiest; a desktop app's executable works too when its framework is installed.
- Run it again when the classes change, e.g. as an npm script: `"models": "lsmsgpack-ts --assembly ... --out src/models.ts"`. For a team, install the tool in a [local tool manifest](https://learn.microsoft.com/dotnet/core/tools/local-tools-how-to-use) (`dotnet new tool-manifest`, `dotnet tool install LsMsgPack.TypeScript`) and run it with `dotnet tool run lsmsgpack-ts`.

Then read with the models:

```ts
import { Decoder } from '@lsmsgpack/client';
import { models, Drawing, Circle } from './models';

const decoder = new Decoder({ models });
const drawing = decoder.decode(bytes).value as Drawing;

for (const shape of drawing.shapes) {
  if (shape instanceof Circle) console.log('circle with radius', shape.radius);
}
```

Objects are now real instances of the generated classes (`instanceof` works), and a value the file doesn't have gets what the .NET constructor sets, exactly as your .NET app reads it. A file written by a newer .NET version than the models is still read: properties the models don't know are added as plain values.

## If JavaScript writes files too

`encode` writes plain MsgPack (maps of property names, no schema):

```ts
import { encode } from '@lsmsgpack/client';

const bytes = encode(drawing, { models }); // instances of the models get the .NET names and types
```

Your .NET app reads those with a second serializer for plain data:

```csharp
LtMsgPackOptions plain = MsgPackMediaTypes.ToPlain(new LtMsgPackOptions());
plain.PropertyNameCaseInsensitive = true; // plain JavaScript objects have camelCase names
LtMsgPackSerializer plainReader = new LtMsgPackSerializer(plain);

Drawing drawing = plainReader.Deserialize<Drawing>(bytes);
```

Keep the two kinds apart (another file extension, or a folder), since a reader has to know whether a file starts with a schema. If both sides write files all the time, using [plain MsgPack files](Setup-FilesPlain.md) in both directions is simpler.

## Changing your classes later

As for [documents](Setup-Documents.md#changing-your-classes-later): adding, removing and reordering properties is safe in both directions, because values are matched by the names in the file's schema. Renaming is not. With generated models, regenerate them after a change; until then, new properties still come through as plain values.

## Watch out

- **Files picked by users are untrusted.** The decoder only creates the generated classes or plain objects, never anything else, and checks lengths and nesting before it allocates. On the .NET side, read files you didn't write yourself as described in [Add-ons](Extras.md#reading-data-you-dont-trust).
- `long` values above 2^53 lose precision as JavaScript numbers: use `new Decoder({ int64: 'bigint' })` (and `--int64 bigint` for the models).
