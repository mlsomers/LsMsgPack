# LtMsgPack

Assembly and package `LtMsgPack`, references only `LsMsgPack.Core` (read `../LsMsgPackCore/CLAUDE.md` for the shared format rules and the trim annotations). `LtMsgPackSerializer` (instance per `LtMsgPackOptions : MsgPackOptions`, the options are copied) writes the **same bytes** as LsMsgPack with the same settings and reads the same values. `CrossLibraryTests` checks bytes and read values for a corpus in all settings (EndianAction × DynamicallyCompact × names/inline/reference): run it after changing either serializer. `Http/` is shared by the web formatters (see `../LsMsgPackFormatters/CLAUDE.md`); the source generator's runtime side (`Generated/`, `Serializer.Generated.cs`) is described in `../LtMsgPack.Generator/CLAUDE.md`.

- **Writing**: `IO/MsgPackWriter` has LsMsgPack's encodings (MpInt with and without DynamicallyCompact, MpString, MpBin, MpFloat, MpDateTime, MpExt). `Writing/`: a typed `ValueHandler<T>` per declared type (no boxing, typed getters via `Delegate.CreateDelegate`), `ObjectPlan` per type. A value of another runtime type goes through `Serializer.WriteBoxed`, which mirrors LsMsgPack's `SerializeObject`/`SerializeCollection`/`SerializeElements` (classification in `TypeKind`, in the order of `MsgPackItem.Pack`) and uses Core's `SerializationRules`. Property and type ids (`WriteContext`): names; `IdMode.Inline` builds the schema of the call in the same order as LsMsgPack's session (`InlineSchema`: a type is added when its property ids are resolved, if it has properties, or when its type id is written; the elements of a wrapped collection come before its type id, so they are written to a rented writer first); `IdMode.Session` uses a Core `SchemaSession` (schema references via `SchemaStore.RunWriter`, or per call with custom property id resolvers or custom dynamic filters).
- **Reading**: typed `ValueReader<T>` (`Reading/`) read the formats they expect and otherwise rewind to the start of the value and read it as LsMsgPack does: `MsgPackReader.ReadPlain` (what `MsgPackItem.UnpackedValue` returns) + Core's `ValueConverter`. `ObjectReader<T>` handles maps with the type id as first key and keys by name or schema index (`BoundSchema` binds the schema's property names to the local properties), and arrays (also wrapped as `{ "": typeId, "@": [...] }`) by position; anything else (a type id elsewhere, `"@"`, custom resolvers) takes the LsMsgPack way (`Slow`). Schemas read inline are cached by their bytes (the options' `SchemaStore` or a private one), with Core's `SchemaStore.Entry.RunReader`.
- **Structs** (`Serializer.StructPlans`: where delegates can be bound or the source generator described the struct (`IGeneratedStruct`), otherwise `BoxedHandler`/`BoxedReader` by reflection): `ObjectHandler<T>`/`ObjectReader<T>` take structs too (no `class` constraint; `typeof(T).IsValueType` tests the JIT drops per instantiation), the object plans write and read a struct **by reference** where they can (`ObjectPlan.ByRef`/`ReadPlan.ByRef`: every property a `RefPropWriter<T>`/`RefPropReader<T>`; reading also needs `StructCreator<T>`, i.e. no declared parameterless constructor and no constructor with values): `ObjectPlan.WriteStruct<T>` and `ObjectReader.ReadByRef`/`ReadPositionalByRef` are copies of only the property loops of `Write`/`WriteArray`/`WriteTrimmed` and `Read`/`ReadPositional` (keep them the same), with `Unsafe.As<RefPropWriter<T>>` per property (`ByRef` guarantees the type: a struct declares all its properties), or the generated code by reference (`Unsafe.As<GeneratedStructCode<T>>(Code)`, see `../LtMsgPack.Generator/CLAUDE.md`), on the caller's parameter or a local, so a struct value allocates nothing. Otherwise (the plans above not given, a struct written as an `object`, the reporting and `Slow` paths) through one box: `StructPropWriter`/`StructPropReader` call the same `StructGetter`/`StructSetter` delegates (Core `LsMsgPack.Generated`: bound open instance delegates, or the generator's lambdas) on `Unsafe.Unbox<T>(box)`, `StructCreator<T>` makes the box. A nested value of the same struct type has its own local or box (read before it is set); computed properties of structs are `StructComputedPropReader<T>`. A struct as the root value is still boxed once per call (the public `Serialize<T>`/`Deserialize<T>` pass the root as an `object`). `LtStructTests.Structs_NoAllocation` checks it; in `BenchmarkGame` by reference instead of the box: sending 57 → 0 B per state and 865 → 0 B per snapshot, reading 122 → 64 B and 2,033 → 1,168 B (MessagePack-CSharp's), the struct rows 7-10% faster (two A/B runs each). The default check (`ObjectHandler.IncludeByDefault`) is `StructDefault<T>`: Core compares `Activator.CreateInstance(type).Equals(value)`, which is `ValueType.Equals`, by reflection for structs with floats, references or padding; it is compiled per type as the same field-by-field comparison (floats `== 0`, so -0.0 is a default and NaN is not, references null, nullables without a value, nested structs, `Equals` of a field type that has its own), Core's boxed comparison for a struct with its own `Equals` or a declared parameterless constructor, and without dynamic code (`PropertyAccessor.CanCompile`; interpreted expressions would gain nothing). The generator writes the same comparison as C# where it sees every field (`GeneratedStructCode.IsDefault`), which `ObjectHandler` prefers: no box also under NativeAOT (`LtStructTests` compares all three with Core on edge cases).
- **Collections**: `List<T>`, `T[]`, exact `HashSet<T>` and `Dictionary<TKey, TValue>` have typed handlers and readers, created by the generator's description or, with dynamic code, `MakeGenericType` (`InstantiateCollection`; neither, e.g. a context of an older version under NativeAOT: boxed). A value that goes through `WriteBoxed` (declared as an interface or `object`) still writes its elements typed (`ITypedElements`, `Serializer.TypedElements`). `CollectionInterfaceReader<T>` reads generic interfaces (`IList<T>`, `IEnumerable<T>`, `ISet<T>`, `IDictionary<,>`...): the wrapper `{ "": typeId, "@": content }` with the reader of that type (`ICollectionContent`), plain data into the interface's concrete type. Anything else rewinds to `Slow`, also for the rules of Core's `ConvertMap`/`ConvertPairs` (`CollectionRules.IsEntryKey`: the keys `""` and `"@"`, nil keys, number keys into string keys; a nil for a value type), for `[SerializeEnumerable]` on the property and for `Unusual` (reporting). Malformed data can differ in the error only (`ArgumentException` for what Core's array conversion reports as `InvalidCastException`, as `List<T>` always did; a type guard names the type instead of the id, as `ObjectReader`; a bad key before a depth error).
- **Options of other libraries** (the defaults write what LsMsgPack writes): `GuidFormat`, `DecimalFormat`, `BigIntegerFormat` (and Core's `UnspecifiedDateTimeKind` and `DateTimeOffsetFormat`, shared), decided per type in `WriteTypeInfo` (kinds `GuidString`, `DecimalString`, `DateTimeOffsetArray`/`DateTimeOffsetMoment`, `BigIntegerBinary`, no cost per value), and the built-in `NerdbankGuidExtension`. Decimals as strings (`DecimalFormat.String`, MessagePack-CSharp's format) are formatted and parsed by `IO/DecimalText` when the mantissa fits in 64 bits (the same text as `decimal.ToString`, the same value and scale as `decimal.Parse`; anything else goes to those). `LtMsgPackPresets` combines them for MessagePack-CSharp, Nerdbank.MessagePack and generic (Python, JS...) peers: `PresetTests` in the interop project checks them against those libraries' defaults (MessagePack-CSharp: the same bytes). Documented in `docs/Compatibility.md`.
- **Differences from LsMsgPack** (documented, by design): custom property id resolvers are asked once per type (plan) in names mode, not per call; duplicate map keys: the last one wins; properties are set in the order of the data; unknown extensions become `MsgPackExtension`; custom extensions derive from `LtExtension<T>` (not `ICustomExt`); no KEEPTRACK.
- netstandard2.0 build: C# 7.3, `Span` from System.Memory, `Unsafe` from System.Runtime.CompilerServices.Unsafe.

## Streaming

`Streaming/` (public, docs/Streaming.md):

- `MsgPackStreamWriter` (tokens into one `MsgPackWriter`, written to the stream at `FlushThreshold`: nothing is ever patched, so any point between calls is safe; a frame stack checks the format; `Position` for an index of the root values; `WriteObject` through `Serializer.Serialize(..., IPayloadSink)`, which hands it the head and body) and `MsgPackStreamReader` (pull tokens over a refilled buffer that keeps the current token, or the mark of a value read whole, and only grows as data arrives; synthesized `ArrayEnd`/`MapEnd` for known lengths; `ReadObject`/`GetValue` frame the value, then replace values of unknown length by known ones (`Plain`, counts kept per start while marked) and pass it to `Deserialize` / `MsgPackReader.ReadPlain`).
- Values of unknown length are the escape sequences of the spec proposal msgpack/msgpack#347 (Core `Streaming/Escape.cs`, the only .NET place with the codes: the PR may still change them, then change `clients/typescript/src/stream-escape.ts` too); the stream reader reads them (and LsMsgPack's items with `ReadStreams`), `MsgPackReader`/`StreamPayload` say so in their 0xC1 error.
- Schema modes (`MsgPackStreamSchemas`): `PerObject` (the payload of `Serialize`, a reference replaced by `SchemaStore.GetInlineSchema`), `PerStream` (inline at first use per stream, then the reference; the reader registers inline schemas in the serializer's store with `RegisterInline`, `GetInline` only caches by bytes), `External` (references, `ReferencedSchemas`). With the indexed schema objects are two values, so only at depth 0, unless a **head** precedes the root value: `WriteHead<TRoot>()` writes the complete schema of the root type once (`Serializer.PrepareHead`: `CompleteSchemas` whatever the options say (a clone, `_completeOptions`), the options' store or `_headStore`; inline/reference as the mode says, `WriteSchema`), the next root value is its body, in which `WriteObject` writes only the value at any depth (`SerializeBody`, the caller passes the declared type of the place); the frozen head session gets cache entries by a thawed copy kept only when its packed schema has the head's id, otherwise the value is refused (`InvalidOperationException`, nothing written). With known lengths the bytes are `Serialize<TRoot>`'s payload. `ReadHead<TRoot>()`/`ReadObject` read it (`Serializer.ReadHead` → `SchemaHead`, `DeserializeBody` binds with the head's root type; `ReadSchema`/`ReadWithSchema` are shared with `DeserializeWithSchema`). Both track `HeadState` (`AwaitingBody`, `InBody`). Tests: `StreamWriterReaderTests` (1-3 byte reads).
- **Index** (docs/Streaming.md "The index"; a feature of this library, not of #347): the model in Core `Streaming/` (namespace `LsMsgPack.Streaming`, so the explorers can show it without LtMsgPack: `MsgPackStreamIndex` documents the layout and field positions, `MsgPackStreamEntry`, `MsgPackStreamIndexPoint`, `MsgPackStreamSchemaLocation`, `MsgPackStreamIndexStatus`, `IMsgPackStreamHasher`/`IMsgPackStreamObserver`, internal `Crc32`), the format in `Streaming/IndexFormat.cs` (writing: encoding, `WriteTail`; reading: `ReadAll` (the last tail from the end, `Search` backwards for a crashed stream, the chain through `PreviousTail`), the content parsed from plain values with validation by Core `Streaming/IndexContent.cs` (`Parse`, `TryParseTail`, `ExtensionHeaderLength`, shared with LsMsgPack's `MpStreamIndex`: the field positions are in `WriteIndex`/`WriteEntry`, there and in `MpStreamIndex.NameOf`, keep the three equal)). The index is an extension value of type 3 (content always in the spec's byte order, `IndexFormat.Options`; its header in the stream's), then the tail `94 cf <u64 offset> ce <u32 length> ce <u32 CRC-32> a4 "LSIX"` (25 bytes, big-endian; `PreviousTail` points to tails, not indexes, because the ext header's length is in the writer's byte order); sidecars are type 4; the relocation delta = where the tail is − (offset + length). Writer (`MsgPackStreamIndexOptions`, `IndexState`): every root value is an entry (`StartEntry` in `Value()` at depth 0 and in `WriteHead`, `EndEntry` in `Done()` when depth 0 and no head waits; a head and its body are one entry), elements of a root array counted in `Count()` (only committed elements; `ElementStart` noted in `Value()`), the hasher and observer fed from `_w` in `FlushBuffer` and `EndEntry` (`FeedFrom`), entries encoded at their end (bad metadata throws there, not in `Dispose`), checkpoints flush the stream, `Dispose` writes `Complete`, or `Interrupted` with the open entry `Incomplete` (not for a refused root value, not after a failed stream write, `_faulted`), `Append` (refuses a crashed or interrupted stream). Reader: `SkipStreamValues` at depth 0 without a mark (in `ReadToken`, `ReadObject`, `ReadHead`, `AtEnd`; `PastStreamValues` peeks when a payload is pending), `ReadIndexes` (registers located schemas, restores the position), `Seek(entry)`, `Seek(entry, point)`, `SeekElement` (`MoveTo` drops the buffer, positions relative to `_origin`). Tests: `StreamIndexTests`.
- **Asynchronous writer** (constructor `asynchronous`, `IsAsynchronous`): `Flushed()` never writes, the buffer goes out only in `FlushIfFullAsync` (at `FlushThreshold`, or a waiting checkpoint: `_checkpoint`), `WriteObjectAsync`, `FlushAsync`, `DisposeAsync` (index + buffer; `IAsyncDisposable` on 2.1/net8.0); `Flush()` throws, `Dispose()` only closes the stream (drops the buffer, no index). Tests `StreamWriterAsyncTests` (same bytes as the sync writer).
- **Asynchronous reader** (`MsgPackStreamReader.Async.cs`): the async methods read ahead, then run the synchronous step with `_noIo` set (`TryEnsure`/`PassPayload` then throw an `InvalidOperationException` instead of reading: a missed read-ahead is a bug, the tests catch it with a stream that refuses synchronous reads). Only the parts that read are there twice (`TryEnsureAsync`, `PassPayloadAsync`, `SkipStreamValuesAsync`, `PastStreamValuesAsync`, `AtEndSlowAsync`): keep them equal to the synchronous ones. A value read whole is buffered by `Scan` (tables `ScanKinds`/`TokenLengths`, a stack of counts, resumes after each refill; stops at data that is not valid, so the synchronous step throws the same error), tokens by `TokenLengths` (no more: a live stream must not wait for the next value). Fast paths without an async method when the buffer decides (`AtEndBuffered`, `PrepareObjectAsync`; `ReadAsync` in an array or map when the token is buffered, `TokenBuffered`; `ReadObjectAsync`/`ReadElementsAsync` of an element all in the buffer, `TryReadObjectBuffered`: its end found once by `BufferedEnd` and handed to `TryPassBuffered` through `_passAt`/`_passEnd`, instead of a `Scan` pass and then `BufferedEnd`; exceptions there become faulted tasks, as in an async method). `AtEnd` in an array of unknown length reads a second byte only after a 0xC1. `ReadElementsAsync` (2.1/net8.0). `ReadHead` takes nil (the payload of null) as the body. `HeadSchemaRead` lets `LtMsgPackHttpSerializer.CreateStreamReader` learn the head's schema for the client. Tests `StreamReaderAsyncTests` (the same tokens, values, objects and errors as the synchronous methods). A value all in the buffer without escapes is framed from its headers alone (`TryPassBuffered` in `ReadObject`, `TryEndBuffered` in `ReadWhole` for `GetValue` of an array or map of known length; `BufferedEnd` with the `Scan` tables), otherwise token by token (`PassValue`, which refills and refuses what is not valid); they leave the reader in the same state (`ObjectsFromTheBuffer_SameStateAsTokenByToken`, `ValuesFromTheBuffer_...`: the `TrickleStream` of the other tests rarely buffers a whole value). In memory (10 000 orders of 5 lines in a head's body, Release, i7-7700K): `ReadObject` per element 0.60 µs (Deserialize of the whole list 0.50 µs per order), `ReadObjectAsync` 0.62 µs. Writing per element (`WriteObject`) 0.39 µs, `Serialize` of the list 0.36 µs.
- Hooks for `LtMsgPack.Data` (internal, `AssemblyInfo.cs` gives it the internals): `MsgPackStreamWriter.WriteHead(byte[] schema, SchemaVersion)` (a head whose schema the caller made: registered with `SchemaStore.AddWritten` in `Serializer.HeadStore()`, indexed and written as `WriteHead(Type)`; `_schemaHead` refuses `WriteObject` in its body), `BeginValue`/`EndValue` (one value written straight into `_w`, the caller rolls `Pos` back on an exception), `Context`, `KeepsIndex`; `MsgPackStreamReader.TryGetHeadSchema`, `GetWhole` (an array or map framed whole, its bytes without escapes, valid until the next read; `WholeValue` shared with `ReadWhole`) and `BufferCurrentAsync` before it. Keep them when changing the head or the bookkeeping (`Value`/`Wrote`).
- Not done yet: escapes in the serializer's own reader (`Deserialize` refuses 0xC1), async `ReadIndexes`/`Seek` (synchronous, need a stream that seeks).

## Performance

Speed relative to System.Text.Json (`BenchmarkInvoices`, 100 invoices × 20 rounds, Release, i7-7700K; STJ source generation writes 1.33x, reads 1.0x):
- Map layout: write 3.1x (indexed) / 3.5x (reference) / 2.9x (names), read 4.2x / 4.4x / 3.8x. Array layout (the default): write 3.7x (indexed) / 4.0x (reference) / 4.2x (no schema), read 4.7-4.9x. Payload 65-69% (indexed), 53-57% (reference), 95% (names). A single `Address` (per call cost): 0.15 µs write and 0.20 µs read (STJ 0.40 / 0.62 µs).
- Other shapes (`lsmsgpack-perf` `lt/LtShapes.cs`; System.Text.Json in brackets): `Dictionary<string, int>` of 20 write 0.36 / read 0.96 µs (0.98 / 2.6), `Dictionary<int, object>` 1.0 / 1.7 µs (5.7 / 9.4), `IList<object>` of 20 1.0 / 1.45 µs (5.5 / 8.3), `HashSet<int>` of 1000 4.7 / 12 µs (13 / 44), `double[]` of 1000 3.5 / 3.3 µs (126 / 81), 30 polymorphic objects 2.6 / 3.4 µs.
- With the source generator (arrays): write 5.6x (indexed) / 6.4x (reference) / 6.3x (no schema), read 5.2-5.8x.
- End to end in ASP.NET Core (TestServer, one invoice per request): ~21 µs per GET and ~34 µs per POST, System.Text.Json ~40 µs / ~52 µs. The framework is most of it.

Found with `perf`, do not undo:
- `UTF8Encoding.GetBytes` costs 10-15 ns per call. Reading checks ASCII with `Ascii.IsValid` and decodes it with `Encoding.Latin1` (net8.0; `UTF8Encoding.GetString` validates in a second pass); writing narrows ASCII with `Ascii.FromUtf16` from 9 chars on (net8.0; non-ASCII continues with the encoder from the first such char, the header stays where it was reserved) and up to 8 chars as two overlapping blocks of 4 or 2 chars (`ShortAscii`, little-endian; otherwise a loop). Throws with formatted messages are in helpers so `EnterContainer`, `ThrowIfUnresolvableAsArray`/`WithSchema` and `MsgPackReader.Count` inline.
- A lambda that captures parameters allocates its closure where the method starts, on every call, also when its path is not taken: the lambdas of the rare paths (`RunReader`/`RunWriter` after a `SchemaGrowthException`, collecting the errors) are in methods of their own (`ReadGrowing`, `WriteGrowing`, `DeserializeCollecting`, `DeserializeBodyCollecting`). They cost 48 B per `Serialize` and 64-120 B per `Deserialize` (one small object with the indexed schema: write 129 → 102 ns, read 157 → 107 ns; `ReadObject` per element 12% less). List them with reflection (`<>c__DisplayClass` types and their fields).
- Polymorphic values: the runtime types seen per declared type are compared before any lookup (`RecentTypes` for the infos in `BoxedHandler`/`ObjectHandler`, `ObjectReader._derived` for the plans and `IsAssignableFrom`, at most 8 each; the hash of a `Type` is a call into the runtime), `WriteTypeInfo.NeverHasTypeId` keeps two dictionary lookups per value, `ObjectPlan.Schema` the schema entry of a type id, `ObjectReader.Typed` the cast that walks the base classes (30 objects of 3 derived types: write 4.1 → 2.6 µs, read 4.4 → 3.4 µs).
- Numbers on the wire are one store with `BinaryPrimitives` (byte by byte had a bounds check per byte, the JIT of .NET 8 does not merge them): `double[]` write 1.7x, read 2.2x; the invoices stay the same (few numbers of more than one byte). 
- Keep the element loop inside `ListHandler.Write`/`ListReader.Read` (`ITypedElements`/`ICollectionContent` call those): in a method of its own, even `AggressiveInlining`, `ObjectPlan.Write` is no longer inlined into the loop by guarded devirtualization and generated code wrote the invoices 2-3% slower.
- `Buffer.BlockCopy` checks types (span copies for keys), `decimal != 0m` is a call (`DecimalHandler.IsZero`), `new T()` of a class is `Activator.CreateInstance` (compiled after 100 calls).
- Per call: the inline schema is recognized by comparing its bytes with the last one (`SchemaHit`), the published session's settings and binding are shared (`SessionShared`), the plans remember their last session binding / ids, `TypeResolver.CacheAssembly` checks lock-free first. The last root type's `FullPropertyInfo`, handler, `WriteTypeInfo` and reader are kept in the per-thread contexts (`WriteContext.RootInfo`/`RootHandler`/`RootTypeInfo`, `ReadContext.RootType`/`RootReader`; not in shared fields, which a server writing several root types would keep overwriting): the hash of a `Type` is a call into the runtime. The read context and its reader are reused per thread (`Serializer.RentContext`, `MsgPackReader.Reset`; the buffer is released after the call), `WriteTypeInfo` keeps the object plans (`PlanOf`), `InlineSchema` has arrays (`List.Clear` called `Array.Clear` per call), and context fields are only stored when they change (a write barrier each). The formatters read the request body from the pipe in place (.NET 8).
- Reading with `out ReadDifferences` (matching data): the copy of the options with the differences is made when a conversion first needs it (`ReadContext.ConversionSettings`, the base settings stay in `SlowSettings`), the public overloads call `ReadDifferences.Collected` in their own try/filter instead of `Collect` with a closure, `ReadDifferences._byKey` is made at the first difference: one `Address` 0.36 → 0.26 µs (0.20 µs without reporting), the invoices 4% less.

Tried without effect: a table of the sizes known from the first byte in `BufferedEnd` before its switch (10-13% of `ReadObject` and the dump reader, mostly mispredicted branches on the data), writing a head's body straight into the stream writer's buffer instead of copying it there (≤1%). Closed `DynamicMethod` delegates instead of open instance ones for getters/setters (<2%, 52 µs to create each), `Ascii.ToUtf16` into a new string instead of `Ascii.IsValid` + Latin-1. Copying decimals in two `ulong` halves in `DecimalHandler` (on x64 Unix a 16 byte struct arrives in two registers and is copied with one 16 byte load, stalling store forwarding: ~7% of reading the invoices in the users' decimal setters, 3% of writing in `PropWriter<T, decimal>.Write`); a decimal-specific `PropWriter` might gain ≤3% on Linux x64 only: not done. The same stall when reading (`DecimalReader`: the JIT promotes the decimal to its 4 + 4 + 8 byte fields, then loads 8 + 8 to pass it on, ~17% of the samples of `ObjectReader.Read`): two `ulong` halves (the JIT then copies the local with one 16 byte move), one `Vector128<byte>` load (promoted again after the cast) and `NoInlining` (the value in registers) all measured the same as before. A `StringPropWriter<TTarget>` calling the sealed `StringHandler` directly (≤1%: PGO's guarded devirtualization already inlines the string handler at that call site).

What remains is mostly allocation (on Linux .NET 8 through coreclr's portable helpers; coreclr's symbols are at `https://debuginfod.ubuntu.com/buildid/<build id>/debuginfo`, its text segment's addresses are the file offsets + 0x1000). Ideas not done: a typed root (no box for a struct as the root value); the virtual calls per property when writing (`PropWriter` → `ValueHandler`; the indirect call is ~7% of writing at one mispredicted call site, the generated code has none); `ToLocalTime` with `ReadDateTimeKind = Local` (~5% of reading; a cache would have to reproduce the offset and the ambiguous-DST bit exactly).
