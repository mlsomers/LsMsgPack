# LsMsgPack

Assembly and package `LsMsgPack`, references only `LsMsgPack.Core` (read `../LsMsgPackCore/CLAUDE.md` for the shared format rules and the trim annotations). `LsMsgPackSerializer` (instance per `LsMsgPackOptions : MsgPackOptions`, the options are copied) writes the **same bytes** as LsMsgPackDebug with the same settings and reads the same values. `CrossLibraryTests` checks bytes and read values for a corpus in all settings (EndianAction × DynamicallyCompact × names/inline/reference): run it after changing either serializer. `Http/` is shared by the web formatters (see `../LsMsgPackFormatters/CLAUDE.md`); the source generator's runtime side (`Generated/`, `Serializer.Generated.cs`) is described in `../LsMsgPack.Generator/CLAUDE.md`.

- **Writing**: `IO/MsgPackWriter` has LsMsgPackDebug's encodings (MpInt with and without DynamicallyCompact, MpString, MpBin, MpFloat, MpDateTime, MpExt). `Writing/`: a typed `ValueHandler<T>` per declared type (no boxing, typed getters via `Delegate.CreateDelegate`), `ObjectPlan` per type. A value of another runtime type goes through `Serializer.WriteBoxed`, which mirrors LsMsgPackDebug's `SerializeObject`/`SerializeCollection`/`SerializeElements` (classification in `TypeKind`, in the order of `MsgPackItem.Pack`) and uses Core's `SerializationRules`. Property and type ids (`WriteContext`): names; `IdMode.Inline` builds the schema of the call in the same order as LsMsgPackDebug's session (`InlineSchema`: a type is added when its property ids are resolved, if it has properties, or when its type id is written; the elements of a wrapped collection come before its type id, so they are written to a rented writer first); `IdMode.Session` uses a Core `SchemaSession` (schema references via `SchemaStore.RunWriter`, or per call with custom property id resolvers or custom dynamic filters).
- **Compiled writers** (`Writing/CompiledWriter.cs`, option `CompileWritersAfter`, default 1000; the readers: see Compiled readers): after that many objects of a plan (`ObjectPlan.CountWrite`, only while `GeneratedPlan` is null, then a read per object) its writer is compiled on the thread pool (`CompileInBackground`; 0: in the plan's constructor, on the caller's thread) and set with one store (`GeneratedPlan`, which holds its `Code`: read it once per object). It is the source generator's contract implemented at runtime: `CompiledObjectCode<T>`/`CompiledStructCode<T>` (a `GeneratedObjectCode<T>`/`GeneratedStructCode<T>`, `Unboxer` set) with a member per plan property, so `Serializer.GeneratedWritePlan` (ids, `Fits`, `Unrolled`, trimming, `Value<T>`/`Runtime`) is reused and the bytes are the generated code's. Per plan, so the code is straight-line (no switch over ids), FilterDefaultValues a constant, one local per value type (a dynamic method zeroes its locals). The leaf kinds come from the same `WriteTypeInfo`s as `Fits` (kind None for `[DefaultValue]`: `Value<T>` asks the boxed filters), properties without an accessible instance getter go to `Runtime`; private getters are read directly (expressions skip visibility). One delegate per kind of call, so the keys are tested per object, not per property: maps (`keys` given, the key written unconditionally), array items (nil for a value left out, trimming: the last value that is not nil marked where the code writes one, the byte check only after the runtime's writers) and unrolled arrays; Guids and decimals in the plan's formats (`GuidFormat.String`, `DecimalFormat.String`: constants, `GeneratedCapabilities.WriteFormats`); the one of the layout is compiled with the plan, the map delegate of an array plan (collections with `SerializeProperties`) at its first call (maps 5-6% faster than one delegate testing `keys` per property). Only where `CompiledWriter.Supported` (`CanCompile` and `IsDynamicCodeCompiled`: not interpreted on WebAssembly), for a type with generated code only where that code writes by its loop over the ids (a property order other than it predicted, properties the static filters leave out...): counted on that path (`GeneratedObjectCode<T>.WriteBoxed`, `WriteStruct`: `GeneratedWritePlan.CountLoop`, `UntilCompiled`, `LoopPlan`), not in `ObjectPlan.Write` (counting there made it too large to be inlined into the loops of collections, a dictionary of objects 8-9% slower); 0 compiles with the plan when the layout of the options is not unrolled (`UnrolledFor`). A class of 120 properties in alphabetical order: 1604-1660 -> 1012-1018 ns. The unrolled generated code stays (maps, `WriteUnrolledMap`, are 9-10% faster than the compiled writers), not with custom dynamic filters or `AddTypeIdOption.Always` (`Serializer.CompileWritersAfter` = -1). A failure keeps the runtime's plan silently: `CompiledWriterTests` check that the writers are used (an `Activator.CreateInstance` overload once made every compile fail while all bytes stayed right). The lt harnesses take `LT_COMPILE_AFTER=n` for the writers and the readers (0 for the equivalence run: every plan compiled).
- **Compiled readers** (`Reading/CompiledReader.cs`, option `CompileReadersAfter`, default 1000; the counterpart of the compiled writers, `Serializer.CompileReadersAfter` -1 without `CompiledWriter.Supported` or with `SlowObjects`): after that many objects of a read plan (`ReadPlan.Create` counts, `CountByRef` for structs read by reference; only while `_untilCompiled` > 0) its reader is compiled on the thread pool (0: in the plan's constructor) and set: `ReadPlan.Code` and `GeneratedRead` first, then `Positional` and `Map`, which are volatile so a thread that sees them also sees the code. It is called through the hooks of the source generator's code in `ObjectReader` (`ReadPositionalBoxed`, `ReadGeneratedMap`, `ReadByRef`, `ReadPositionalByRef`). `CompiledObjectReader<T>` derives from `GeneratedObjectCode` itself (one virtual call and the delegate per object), `CompiledStructReader<T>` from `GeneratedStructCode<T>` (by reference, a box through its `Unboxer`). Its members are the plan's properties by position (`PropReader.CompiledId`; `GeneratedId` stays -1, so the per value path of `ObjectReader`'s loops never calls this code). A value is read here when its type is one the generated readers read themselves (`Serializer.ReadKind`: `CompiledWriter.KindOf` and `Fits` for reading; the same `MsgPackReader`/`GeneratedIO` calls as `Emitter.ReadValue`) and the member can be assigned by an expression (any visibility, init-only setters; not readonly fields, static or computed members); every other value, and a value in another format (the position is left at its start), is read by the property's `PropReader`: the same values, conversions and errors. **Arrays** are straight-line code: position t is the plan's property t, for the first `CompiledReads.Limit(props)` positions (how far the array of properties, the plan's own or its binding to the schema, equals the plan's order: checked once per array), `CompiledReader.Rest` (the runtime's loop) reads the positions after them, so a class with properties added at the end on either side keeps the compiled code. **Maps** with the indexed schema: a loop over the keys with a switch over `CompiledId`, the key (a positive fixint) read inline, any other key by `GeneratedIO.TryReadKey`. **Maps keyed by names** (`CompiledReader.Names`, `CompiledReads.Keys`) straight-line: the code of property t reads the next entry when its key is property t's name with the header of a string as the writers write it (`CompiledReader.Key`), compared as constants (`GeneratedIO.KeyIs`, public since the generated code of contract version 5 calls it too: words of 8/4/2/1 bytes at 0, 8, 16 and the last one, read little-endian whatever the machine, up to 32 bytes, which the JIT inlines with the constants; longer keys `GeneratedIO.LongKeyIs`), so a property FilterDefaultValues left out costs one failed comparison; the entries after the first key that is not the next property's (another order, keys the class does not have, duplicates, other string headers, `""`/`"@"`) go to `CompiledReader.Entries` from the last matched property (the runtime's loop: `FindByName`, the same values, restarts and errors). Not with `PropertyNameCaseInsensitive` (`ReadPlan.Map` stays false, its rules stay in `ObjectReader.Read`); with `c.Schema` set the delegate hands everything to `Entries`. The layout the options do not write is compiled when its first object is read (`CompiledReads.Ask`: on the thread pool, the runtime's loop reads until then; with 0 at once; a failure keeps the runtime's loop). Not for types with generated code (it is used), plans created by a constructor with values (`WithValues`) and types without a member read here (`CompiledReader.Create` returns null). The web formatters compile them when a type is first read (`LsMsgPackHttpOptions.CompileReadersAfter` 0, as for the writers: the JIT then profiles the object loops with the compiled readers in place). Invoices, read, A/B on .NET 8 (one candidate per process): default options 5.7-5.8 -> 4.4-4.5 ms, arrays without the schema 5.5 -> 4.35 ms, maps with the indexed schema 5.5-5.9 -> 4.8-5.0 ms, with references 5.65 -> 4.95 ms, maps with names 6.77-6.88 -> 4.69-4.73 ms (a class of 120 properties with 4 left out, `Generic()` preset: 2640-2715 -> 1389-1413 ns; game messages with names: a state 258 -> 160 ns, a snapshot 3.7 -> 2.2 µs); the generated code's 4.56-4.69 / 5.04-5.23 / 4.60-4.66 ms (names: the same straight-line code since contract version 5, see `../LsMsgPack.Generator/CLAUDE.md`; before it 6.4-6.7 ms by its loop over the keys). Tried: maps as a chain of the properties' code with a call per key (`TryReadKey`: names 7.0 -> 7.9 ms, indexed 5.8 -> 6.0 ms), names by a loop over the keys with the key compared inline (6.8 -> 6.7 ms: about the same number of instructions as the runtime's loop, `perf stat`). In one process with other setups (`table` mode, `BenchmarkInvoices`) the rows that do not use the compiled readers (generated code, reporting) read 2-11% slower than the same rows of the base, one candidate per process ±2%: the shared JIT profile. Tests: `CompiledReaderTests` (used; the same values and errors as the runtime's readers for every kind, other formats and classes, data that ends anywhere, structs, threads; `MapsWithNames_ReadAsTheRuntimesPlans`: keys of every length `KeyIs` compares, twins that differ in one word only, other orders and headers), `CrossLibraryTests` ("Compiled": readers and writers from the first object).
- **Reading**: typed `ValueReader<T>` (`Reading/`) read the formats they expect and otherwise rewind to the start of the value and read it as LsMsgPackDebug does: `MsgPackReader.ReadPlain` (what `MsgPackItem.UnpackedValue` returns) + Core's `ValueConverter`. `ObjectReader<T>` handles maps with the type id as first key and keys by name or schema index (`BoundSchema` binds the schema's property names to the local properties), and arrays (also wrapped as `{ "": typeId, "@": [...] }`) by position; anything else (a type id elsewhere, `"@"`, custom resolvers) takes the LsMsgPackDebug way (`Slow`). Values declared as `object` have an `ObjectReader<object>` too: a map with a type id is read by the plan of that type (`Derived`, the type guard as declared `object`), everything else `Slow` (`object` has no read plan: Core keeps a map without a type id as the raw map; with `Unusual` always `Slow`, Core reports them); 4 `object` properties with a nested object 0.97 → 0.41 µs. Keys by name: `ReadPlan.FindByName` tries the next property, then searches forward from it and wraps around (`Search`): the values FilterDefaultValues leaves out skip properties, and a search from the last property backwards made a class of 120 properties with 4 values left out read 1.6x slower (generated 2862-2880 -> 1765-1777 ns, runtime readers 3556-3566 -> 2135-2136 ns, A/B on .NET 8); `FindOrMatchIgnoringCase` the same. Schemas read inline are cached by their bytes (the options' `SchemaStore` or a private one), with Core's `SchemaStore.Entry.RunReader`.
- **Structs** (`Serializer.StructPlans`: where delegates can be bound or the source generator described the struct (`IGeneratedStruct`), otherwise `BoxedHandler`/`BoxedReader` by reflection): `ObjectHandler<T>`/`ObjectReader<T>` take structs too (no `class` constraint; `typeof(T).IsValueType` tests the JIT drops per instantiation), the object plans write and read a struct **by reference** where they can (`ObjectPlan.ByRef`/`ReadPlan.ByRef`: every property a `RefPropWriter<T>`/`RefPropReader<T>`; reading also needs `StructCreator<T>`, i.e. no declared parameterless constructor and no constructor with values): `ObjectPlan.WriteStruct<T>` and `ObjectReader.ReadByRef`/`ReadPositionalByRef` are copies of only the property loops of `Write`/`WriteArray`/`WriteTrimmed` and `Read`/`ReadPositional` (keep them the same), with `Unsafe.As<RefPropWriter<T>>` per property (`ByRef` guarantees the type: a struct declares all its properties), or the generated code by reference (`Unsafe.As<GeneratedStructCode<T>>(generated.Code)`, also the compiled writers, see `../LsMsgPack.Generator/CLAUDE.md`), on the caller's parameter or a local, so a struct value allocates nothing. Otherwise (the plans above not given, a struct written as an `object`, the reporting and `Slow` paths) through one box: `StructPropWriter`/`StructPropReader` call the same `StructGetter`/`StructSetter` delegates (Core `LsMsgPack.Generated`: bound open instance delegates, or the generator's lambdas) on `Unsafe.Unbox<T>(box)`, `StructCreator<T>` makes the box. A nested value of the same struct type has its own local or box (read before it is set); computed properties of structs are `StructComputedPropReader<T>`. A struct as the root value of the typed calls (`Serialize<T>`/`Deserialize<T>`, the stream writer's `WriteObject<T>` and reader's `ReadObject<T>`; not `Nullable<T>`) is not boxed either: the entry code passes the root as an `object`, so it is a `RootSlot<T>` kept in the per-thread state the call rents anyway (`Serializer.WriteState.Slot`, `ReadContext.Slot`; a nested call has its own), `WriteContext.Root` when writing (`TypedWriter<T>.SerializeInSlot` rents the state itself and calls the `Serialize` overload taking it), and when reading `ReadContext.IntoSlot` makes `ReadRoot` call `ValueReader.ReadIntoSlot` and return the slot, which `RootSlot<T>.Take` reads (it takes a boxed result too: the paths that collect differences or errors read boxed, since `ReadDifferences.Root` keeps the result, and an unconverted root value still fails the cast). The callers test `typeof(T).IsValueType && RootSlot<T>.IsPlainStruct` in their own body: a helper method with that test was not inlined into shared code (a call per `Deserialize` of a class, 3-5%), and the slot in a `[ThreadStatic]` of its own (three more thread static accesses per call) made struct roots 8% slower than the box. `LsStructTests.Structs_NoAllocation`, `StructRoot_NoAllocation` and `StructRoot_SameAsBoxed` check it; in `BenchmarkGame` by reference instead of the box: sending 57 → 0 B per state and 865 → 0 B per snapshot, reading 122 → 64 B and 2,033 → 1,168 B (MessagePack-CSharp's), the struct rows 7-10% faster (two A/B runs each). The default check (`ObjectHandler.IncludeByDefault`) is `StructDefault<T>`: Core compares `Activator.CreateInstance(type).Equals(value)`, which is `ValueType.Equals`, by reflection for structs with floats, references or padding; it is compiled per type as the same field-by-field comparison (floats `== 0`, so -0.0 is a default and NaN is not, references null, nullables without a value, nested structs, `Equals` of a field type that has its own), Core's boxed comparison for a struct with its own `Equals` or a declared parameterless constructor, and without dynamic code (`PropertyAccessor.CanCompile`; interpreted expressions would gain nothing). The generator writes the same comparison as C# where it sees every field (`GeneratedStructCode.IsDefault`), which `ObjectHandler` prefers: no box also under NativeAOT (`LsStructTests` compares all three with Core on edge cases).
- **Fields** (docs/schema.md "Fields"; a field is a property in the format, `FullPropertyInfo.FieldInfo`): `PropWriter.CreateForField`/`PropReader.CreateForField` ask the generated code first (`GeneratedTypes.FindMember`, not for a readonly field when reading), otherwise compile typed delegates from expression trees (Core `Meta/FieldDelegates.cs`: `Getter`/`Setter`/`StructGetter`/`StructSetter`) through the constructors taking a `FieldInfo` of `PropWriter<,>`, `StructPropWriter<,>`, `PropReader<,>`, `StructPropReader<,>` (structs by reference, so the by-reference plans work). They are compiled **when the plan is built**, not after some uses as Core's `PropertyAccessor` does for its 100 calls: PGO then profiles the final code from the start, a delegate swapped in later is never re-profiled. Cost at cold start about 0.5 ms per field (getter, setter and the struct's; the first write and read of two types with 11 fields +2 to +14 ms). A readonly field has no setter: `BoxedPropReader`, as get-only properties. Without dynamic code (`CanBindDelegates`) or for an open generic declaring type (as for properties): `BoxedPropWriter`/`BoxedPropReader`. `CompiledWriter` reads a field as it reads a property (`Expression.MakeMemberAccess`, a struct by reference). `StructDefault.TypedEquals`: a framework struct with its own `Equals` that implements `IEquatable<T>` (`Vector3`, `Quaternion`, the matrices) is compared with `default(T)` typed, without a box (Vector3 members allocated 32 B per write otherwise), the same as the generator's `IsDefault`; `LsStructTests.DefaultCheck_FrameworkStructs_SameAsCore` compares with Core for -0, NaN and denormals. Measured (game state of 8 fields and 2 struct fields of 3 floats, Release): runtime plans with fields equal those with properties (.NET 8 write 158-162 vs 161-163 ns, read 184-186 vs 182-188; .NET 10 write 151 vs 154-156, read 163 vs 166); compiled writers per piece equal. Tests: `LsStructTests.FieldStructs_NoAllocation`, `CrossLibraryTests.SameBytesAndValuesFields`.
- **Collections**: `List<T>`, `T[]`, exact `HashSet<T>` and `Dictionary<TKey, TValue>` have typed handlers and readers, created by the generator's description or, with dynamic code, `MakeGenericType` (`InstantiateCollection`; neither, e.g. a context of an older version under NativeAOT: boxed). **Arrays, lists and sets in bulk** (`Serializer.Bulk`/`InBulk`, `NumberHandler`/`NumberReader`, asked before the others; `T[]`, `List<T>` on net8.0 only (`CollectionsMarshal`), exact `HashSet<T>`): of `int`, `long`, `float`, `double` (written the same with any options), and of `sbyte` (lists: an `sbyte[]` is bin), `short`, `ushort`, `uint`, `ulong`, `bool`, `Guid` and `decimal` when their `TypeKind` is the plain one (not with a custom extension, nor `GuidFormat.String`/`DecimalFormat.String`; decimals with the built-in `DecimalExtension`, not type code -1, its code passed along as `decimalCode`); one switch over the element types for all three (`WithBulkElement` with an `IBulkCreator` struct, no dynamic code). `NumberArrayHandler<T>`/`NumberListHandler<T>`/`NumberSetHandler<T>` (a set: `CopyTo` into a pooled array, the order it enumerates) call `MsgPackWriter.Int32s`/`Int64s`/`Singles`/`Doubles`/`Integers<T>`/`Bools`/`Guids`/`Decimals` (the space checked per block of 1024 values, the position in a local, the same bytes as a call per value), `NumberArrayReader<T>`/`NumberListReader<T>`/`NumberSetReader<T>` (blocks of 32 on the stack, then `Add`) call `MsgPackReader.ReadInt32s`/.../`ReadIntegers<T>`/`ReadBools`/`ReadGuids`/`ReadDecimals` (the values in the formats the type's reader reads directly in one loop, read by reference: the end is checked against the buffer once, each value against the end; integers out of the type's range stop it), which stop at the first value in another format or cut off: the reader of the element type reads that one (nil, conversions, overflow, the errors), then the loop goes on. Guids and decimals are copied as they are in memory (Guids: little-endian machines only, the order of `ToByteArray`). 1000 values, write / read, A/B on .NET 8: `int[]` 5.3 -> 2.2 / 8.0 -> 2.4 µs, `long[]` 6.1 -> 3.3 / 7.7 -> 3.9 µs, `float[]` 2.5 -> 1.2 / 3.0 -> 1.4 µs, `double[]` 2.8 -> 1.4 / 4.2 -> 2.3 µs, `short[]` 5.8-6.7 -> 2.9-3.0 / 8.3-9.6 -> 3.8 µs, `uint[]` 5.1-5.7 -> 2.8 / 7.5-8.6 -> 3.1-3.2 µs, `bool[]` 2.0 -> 1.0-1.1 / 2.1-2.7 -> 1.3 µs, `Guid[]` 5.3-5.5 -> 1.8-1.9 / 8.8-9.1 -> 2.5-2.8 µs, `decimal[]` 4.3 -> 1.85 / 4.7 -> 2.1 µs, `HashSet<int>` 5.3-6.3 -> 4.0-4.5 / 12.5-13.6 -> 8.7-9.4 µs (its enumerator in blocks wrote 5.0-5.1 µs), lists the same; what remains is the payload's copy and allocating the collection. Not `DateTime[]` (a loop without the call per value: write 8.0 -> 7.3-7.6 µs, read the same; the timestamp is most of it) nor `Dictionary<string, int>` (keys and values alternate; a string and a hash insert per entry). A value that goes through `WriteBoxed` (declared as an interface or `object`) still writes its elements typed (`ITypedElements`, `Serializer.TypedElements`). `CollectionInterfaceReader<T>` reads generic interfaces (`IList<T>`, `IEnumerable<T>`, `ISet<T>`, `IDictionary<,>`...): the wrapper `{ "": typeId, "@": content }` with the reader of that type (`ICollectionContent`), plain data into the interface's concrete type. Anything else rewinds to `Slow`, also for the rules of Core's `ConvertMap`/`ConvertPairs` (`CollectionRules.IsEntryKey`: the keys `""` and `"@"`, nil keys, number keys into string keys; a nil for a value type), for `[SerializeEnumerable]` on the property and for `Unusual` (reporting). Malformed data can differ in the error only (`ArgumentException` for what Core's array conversion reports as `InvalidCastException`, as `List<T>` always did; a type guard names the type instead of the id, as `ObjectReader`; a bad key before a depth error).
- **Options of other libraries** (the defaults write what LsMsgPackDebug writes): `GuidFormat`, `DecimalFormat`, `BigIntegerFormat` (and Core's `UnspecifiedDateTimeKind` and `DateTimeOffsetFormat`, shared), decided per type in `WriteTypeInfo` (kinds `GuidString`, `DecimalString`, `DateTimeOffsetArray`/`DateTimeOffsetMoment`, `BigIntegerBinary`, no cost per value), and the built-in `NerdbankGuidExtension`. Guids as strings are formatted as UTF-8 in place on net8.0 (`Guid.TryFormat` into the buffer) and parsed from UTF-8 by `IO/GuidText` when they are in the format "D" (str 8 of 36 bytes, `MsgPackReader.TryReadGuidString`; Vector128 on net8.0: 37 -> 9.5 ns per Guid, a table per digit elsewhere: 21.5 ns; `Utf8Parser` measured as slow as `Guid.TryParse` of the chars), anything else goes to `Guid.TryParse` of the chars (other formats, white space, the `+`/`0x` it takes inside the groups, the errors). 1M fuzzed texts each through the vector and the table path: the same values and errors as `Guid.TryParse`. Decimals as strings (`DecimalFormat.String`, MessagePack-CSharp's format) are formatted and parsed by `IO/DecimalText` when the mantissa fits in 64 bits (the same text as `decimal.ToString`, the same value and scale as `decimal.Parse`; anything else goes to those). `LsMsgPackPresets` combines them for MessagePack-CSharp, Nerdbank.MessagePack and generic (Python, JS...) peers: `PresetTests` in the interop project checks them against those libraries' defaults (MessagePack-CSharp: the same bytes). Documented in `docs/Compatibility.md`.
- **`FilterShouldSerialize`** is not a custom filter mode (`Serializer.IMsgPackPropertyIncludeDynamicallyArray` skips it): only the properties with a method (`Serializer.CallsShouldSerialize`) are filtered by it, the other properties keep the typed, generated and compiled paths. When the filters are exactly `[FilterShouldSerialize]`, `[FilterDefaultValues, FilterShouldSerialize]` or `[FilterShouldSerialize, FilterDefaultValues]` (`Serializer.TypedShouldSerializeFilter`) and the method has a typed delegate on the class declaring the property (Core `ShouldSerializeMethod.Typed`/`OwnerType`: an instance method of a class with dynamic code), `PropWriter<,,>` calls it typed (filter modes `ShouldSerializeFilter`, `ShouldSerializeThenDefaultsFilter`, `DefaultsThenShouldSerializeFilter`: the order in which `MsgPackOptions.IncludeDynamically` asks them, the last filter first, so the method is called as often), and the compiled writers call it in their expressions for the values they write themselves (`ShouldSerializeCalls`, `Builder.LeftOut`; `WriteMember` lets compiled code through); a value they leave to the runtime (`GeneratedWritePlan.Value` has no owner) keeps `canWrite` false. A `[DefaultValue]` (with `FilterDefaultValues`), other filters, structs and static methods: `BoxedFilter` with the owner (`PropWriter.IncludeBoxed(value, info, owner)`; structs boxed only when `OwnerFilters`). The generator's getters have no instantiations of the typed modes (`LsGeneratedProperty.CreateWriter` returns null for them, `PropWriter.Create` binds the getter; NativeAOT has no typed delegates), the generated code leaves the properties to the runtime (`WriteMember` -1). A list of 1000 objects of 8 properties, 3 with a method (A/B on .NET 8): arrays 118-133 -> 47-49 µs, maps 136-149 -> 68-70 µs (with `FilterDefaultValues` only: 55-66 / 138-142 µs, writing more), no box per value (-24 KB per call). LsMsgPackDebug's array layout does not ask the filters for a null value, LsMsgPack does (same bytes; `ShouldSerializeTests.CallsTheMethodsAsLsMsgPack` compares the calls with LsMsgPackDebug's map layout). Other `IMsgPackPropertyIncludeWithOwner` filters are custom (boxed, no generated or compiled writers).
- **Differences from LsMsgPackDebug** (documented, by design): custom property id resolvers are asked once per type (plan) in names mode, not per call; duplicate map keys: the last one wins; properties are set in the order of the data; unknown extensions become `MsgPackExtension`; custom extensions derive from `LsExtension<T>` (not `ICustomExt`); no KEEPTRACK.
- netstandard2.0 build: C# 7.3, `Span` from System.Memory, `Unsafe` from System.Runtime.CompilerServices.Unsafe.

## Streaming

`Streaming/` (public, docs/Streaming.md):

- `MsgPackStreamWriter` (tokens into one `MsgPackWriter`, written to the stream at `FlushThreshold`: nothing is ever patched, so any point between calls is safe; a frame stack checks the format; `Position` for an index of the root values; `WriteObject` through `Serializer.Serialize(..., IPayloadSink)`, which hands it the head and body) and `MsgPackStreamReader` (pull tokens over a refilled buffer that keeps the current token, or the mark of a value read whole, and only grows as data arrives; synthesized `ArrayEnd`/`MapEnd` for known lengths; `ReadObject`/`GetValue` frame the value, then replace values of unknown length by known ones (`Plain`, counts kept per start while marked) and pass it to `Deserialize` / `MsgPackReader.ReadPlain`).
- Values of unknown length are the escape sequences of the spec proposal msgpack/msgpack#347 (Core `Streaming/Escape.cs`, the only .NET place with the codes: the PR may still change them, then change `clients/typescript/src/stream-escape.ts` too); the stream reader reads them (and LsMsgPackDebug's items with `ReadStreams`), `MsgPackReader`/`StreamPayload` say so in their 0xC1 error.
- Schema modes (`MsgPackStreamSchemas`): `PerObject` (the payload of `Serialize`, a reference replaced by `SchemaStore.GetInlineSchema`), `PerStream` (inline at first use per stream, then the reference; the reader registers inline schemas in the serializer's store with `RegisterInline`, `GetInline` only caches by bytes), `External` (references, `ReferencedSchemas`). With the indexed schema objects are two values, so only at depth 0, unless a **head** precedes the root value: `WriteHead<TRoot>()` writes the complete schema of the root type once (`Serializer.PrepareHead`: `CompleteSchemas` whatever the options say (a clone, `_completeOptions`), the options' store or `_headStore`; inline/reference as the mode says, `WriteSchema`), the next root value is its body, in which `WriteObject` writes only the value at any depth (`SerializeBody`, the caller passes the declared type of the place); the frozen head session gets cache entries by a thawed copy kept only when its packed schema has the head's id, otherwise the value is refused (`InvalidOperationException`, nothing written). With known lengths the bytes are `Serialize<TRoot>`'s payload. `ReadHead<TRoot>()`/`ReadObject` read it (`Serializer.ReadHead` → `SchemaHead`, `DeserializeBody` binds with the head's root type; `ReadSchema`/`ReadWithSchema` are shared with `DeserializeWithSchema`). Both track `HeadState` (`AwaitingBody`, `InBody`). Tests: `StreamWriterReaderTests` (1-3 byte reads).
- **Index** (docs/Streaming.md "The index"; a feature of this library, not of #347): the model in Core `Streaming/` (namespace `LsMsgPack.Streaming`, so the explorers can show it without LsMsgPack: `MsgPackStreamIndex` documents the layout and field positions, `MsgPackStreamEntry`, `MsgPackStreamIndexPoint`, `MsgPackStreamSchemaLocation`, `MsgPackStreamIndexStatus`, `IMsgPackStreamHasher`/`IMsgPackStreamObserver`, internal `Crc32`), the format in `Streaming/IndexFormat.cs` (writing: encoding, `WriteTail`; reading: `ReadAll` (the last tail from the end, `Search` backwards for a crashed stream, the chain through `PreviousTail`), the content parsed from plain values with validation by Core `Streaming/IndexContent.cs` (`Parse`, `TryParseTail`, `ExtensionHeaderLength`, shared with LsMsgPackDebug's `MpStreamIndex`: the field positions are in `WriteIndex`/`WriteEntry`, there and in `MpStreamIndex.NameOf`, keep the three equal)). The index is an extension value of type 3 (content always in the spec's byte order, `IndexFormat.Options`; its header in the stream's), then the tail `94 cf <u64 offset> ce <u32 length> ce <u32 CRC-32> a4 "LSIX"` (25 bytes, big-endian; `PreviousTail` points to tails, not indexes, because the ext header's length is in the writer's byte order); sidecars are type 4; the relocation delta = where the tail is − (offset + length). Writer (`MsgPackStreamIndexOptions`, `IndexState`): every root value is an entry (`StartEntry` in `Value()` at depth 0 and in `WriteHead`, `EndEntry` in `Done()` when depth 0 and no head waits; a head and its body are one entry), elements of a root array counted in `Count()` (only committed elements; `ElementStart` noted in `Value()`), the hasher and observer fed from `_w` in `FlushBuffer` and `EndEntry` (`FeedFrom`), entries encoded at their end (bad metadata throws there, not in `Dispose`), checkpoints flush the stream, `Dispose` writes `Complete`, or `Interrupted` with the open entry `Incomplete` (not for a refused root value, not after a failed stream write, `_faulted`), `Append` (refuses a crashed or interrupted stream; `AppendAsync` reads the chain with `ReadAllAsync` and returns an asynchronous writer, `AppendOptions`/`ContinueAfter` shared; `ReadAll`/`ReadAllAsync` return an `IndexChain` with the last tail, whether the stream ends with it and the delta). Reader: `SkipStreamValues` at depth 0 without a mark (in `ReadToken`, `ReadObject`, `ReadHead`, `AtEnd`; `PastStreamValues` peeks when a payload is pending), `ReadIndexes` (registers located schemas, restores the position), `Seek(entry)`, `Seek(entry, point)`, `SeekElement` (`MoveTo` drops the buffer, positions relative to `_origin`). Async: `ReadIndexesAsync` (`IndexFormat.ReadAllAsync`, `TryReadAtAsync`, `SearchAsync` (they return a `Found`: async methods have no out parameters): the checks shared with the sync ones, `TryTail`/`TryParse`/`PreviousTail`/`MayBeTail`, keep the reads equal), `SeekElementAsync` (`CheckSeekElement`, `SeekPointBefore` shared); the two `Seek`s read nothing, so they have no async variant. Tests: `StreamIndexTests` (`Indexes` reads every index also with `ReadIndexesAsync` from a seeking stream that refuses synchronous reads: the same indexes or the same error).
- **Asynchronous writer** (constructor `asynchronous`, `IsAsynchronous`): `Flushed()` never writes, the buffer goes out only in `FlushIfFullAsync` (at `FlushThreshold`, or a waiting checkpoint: `_checkpoint`), `WriteObjectAsync`, `FlushAsync`, `DisposeAsync` (index + buffer; `IAsyncDisposable` on 2.1/net8.0); `Flush()` throws, `Dispose()` only closes the stream (drops the buffer, no index). Tests `StreamWriterAsyncTests` (same bytes as the sync writer).
- **Asynchronous reader** (`MsgPackStreamReader.Async.cs`): the async methods read ahead, then run the synchronous step with `_noIo` set (`TryEnsure`/`PassPayload` then throw an `InvalidOperationException` instead of reading: a missed read-ahead is a bug, the tests catch it with a stream that refuses synchronous reads). Only the parts that read are there twice (`TryEnsureAsync`, `PassPayloadAsync`, `SkipStreamValuesAsync`, `PastStreamValuesAsync`, `AtEndSlowAsync`): keep them equal to the synchronous ones. A value read whole is buffered by `Scan` (tables `ScanKinds`/`TokenLengths`, a stack of counts, resumes after each refill; stops at data that is not valid, so the synchronous step throws the same error), tokens by `TokenLengths` (no more: a live stream must not wait for the next value). Fast paths without an async method when the buffer decides (`AtEndBuffered`, `PrepareObjectAsync`; `ReadAsync` in an array or map when the token is buffered, `TokenBuffered`; `ReadObjectAsync`/`ReadElementsAsync` of an element all in the buffer, `TryReadObjectBuffered`: its end found once by `BufferedEnd` and handed to `TryPassBuffered` through `_passAt`/`_passEnd`, instead of a `Scan` pass and then `BufferedEnd`; exceptions there become faulted tasks, as in an async method). `AtEnd` in an array of unknown length reads a second byte only after a 0xC1. `ReadElementsAsync` (2.1/net8.0). `ReadHead` takes nil (the payload of null) as the body. `HeadSchemaRead` lets `LsMsgPackHttpSerializer.CreateStreamReader` learn the head's schema for the client. Tests `StreamReaderAsyncTests` (the same tokens, values, objects and errors as the synchronous methods). A value all in the buffer without escapes is framed from its headers alone (`TryPassBuffered` in `ReadObject`, `TryEndBuffered` in `ReadWhole` for `GetValue` of an array or map of known length; `BufferedEnd` with the `Scan` tables), otherwise token by token (`PassValue`, which refills and refuses what is not valid); they leave the reader in the same state (`ObjectsFromTheBuffer_SameStateAsTokenByToken`, `ValuesFromTheBuffer_...`: the `TrickleStream` of the other tests rarely buffers a whole value). In memory (10 000 orders of 5 lines in a head's body, Release, i7-7700K): `ReadObject` per element 0.60 µs (Deserialize of the whole list 0.50 µs per order), `ReadObjectAsync` 0.62 µs. Writing per element (`WriteObject`) 0.39 µs, `Serialize` of the list 0.36 µs.
- Hooks for `LsMsgPack.Data` (internal, `AssemblyInfo.cs` gives it the internals): `MsgPackStreamWriter.WriteHead(byte[] schema, SchemaVersion)` (a head whose schema the caller made: registered with `SchemaStore.AddWritten` in `Serializer.HeadStore()`, indexed and written as `WriteHead(Type)`; `_schemaHead` refuses `WriteObject` in its body), `BeginValue`/`EndValue` (one value written straight into `_w`, the caller rolls `Pos` back on an exception), `Context`, `KeepsIndex`; `MsgPackStreamReader.TryGetHeadSchema`, `GetWhole` (an array or map framed whole, its bytes without escapes, valid until the next read; `WholeValue` shared with `ReadWhole`) and `BufferCurrentAsync` before it. ## Performance

Speed relative to System.Text.Json (`BenchmarkInvoices`, 100 invoices × 20 rounds, Release, .NET 10, i7-7700K, one run of 2026-11-11; STJ source generation writes 1.29x, reads 1.0x):
- Map layout: write 3.9x (indexed) / 3.9x (reference) / 3.8x (names), read 5.4x / 5.6x / 5.5x. Array layout (the default): write 4.7x (indexed) / 5.4x (reference) / 5.7x (no schema), read 6.0-6.3x. Payload 65-69% (indexed), 53-57% (reference), 95% (names). A single `Address` (per call cost): 0.15 µs write and 0.20 µs read (STJ 0.40 / 0.62 µs).
- Other shapes (`lsmsgpack-perf` `fast/LsShapes.cs`, .NET 8, 2026-11-11; System.Text.Json in brackets): `Dictionary<string, int>` of 20 write 0.36 / read 0.91 µs (1.1 / 2.5), `Dictionary<int, object>` 0.74 / 1.45 µs (6.1 / 9.6), `IList<Item>` of 20 0.71 / 1.2 µs (5.6 / 8.4), `HashSet<int>` of 1000 3.8 / 8.5 µs (13 / 43), `double[]` of 1000 1.3 / 2.3 µs (126 / 84), 30 polymorphic objects 1.9 / 2.5 µs.
- With the source generator (arrays): write 4.8x (indexed) / 5.8x (reference) / 5.3x (no schema), read 6.0-6.1x; maps with names read 5.9x (straight-line since contract version 5, a run later that day; the runtime's names 5.4x in that run). In one process with the other setups, as here, the generated readers and the compiled ones share call sites: one setup per process they read arrays equally fast.
- End to end in ASP.NET Core (TestServer, one invoice per request): ~21 µs per GET and ~34 µs per POST, System.Text.Json ~40 µs / ~52 µs. The framework is most of it.

Found with `perf`, do not undo:
- `UTF8Encoding.GetBytes` costs 10-15 ns per call. Reading checks ASCII with `Ascii.IsValid` and decodes it with `Encoding.Latin1` (net8.0; `UTF8Encoding.GetString` validates in a second pass); writing narrows ASCII with `Ascii.FromUtf16` from 9 chars on (net8.0; non-ASCII continues with the encoder from the first such char, the header stays where it was reserved) and up to 8 chars as two overlapping blocks of 4 or 2 chars (`ShortAscii`, little-endian; otherwise a loop). Throws with formatted messages are in helpers so `EnterContainer`, `ThrowIfUnresolvableAsArray`/`WithSchema` and `MsgPackReader.Count` inline.
- A lambda that captures parameters allocates its closure where the method starts, on every call, also when its path is not taken: the lambdas of the rare paths (`RunReader`/`RunWriter` after a `SchemaGrowthException`, collecting the errors) are in methods of their own (`ReadGrowing`, `WriteGrowing`, `DeserializeCollecting`, `DeserializeBodyCollecting`). They cost 48 B per `Serialize` and 64-120 B per `Deserialize` (one small object with the indexed schema: write 129 → 102 ns, read 157 → 107 ns; `ReadObject` per element 12% less). List them with reflection (`<>c__DisplayClass` types and their fields).
- Polymorphic values: the runtime types seen per declared type are compared before any lookup (`RecentTypes` for the infos in `BoxedHandler`/`ObjectHandler`, `ObjectReader._derived` for the plans and `IsAssignableFrom`, at most 8 each; the hash of a `Type` is a call into the runtime), `WriteTypeInfo.NeverHasTypeId` keeps two dictionary lookups per value, `ObjectPlan.Schema` the schema entry of a type id, `ObjectReader.Typed` the cast that walks the base classes (30 objects of 3 derived types: write 4.1 → 2.6 µs, read 4.4 → 3.4 µs).
- Small messages of numbers (`BenchmarkGame`, `fast/LsGame.cs`, A/B on .NET 8 of a state / a snapshot): `ObjectPlan.WriteStruct` is `NoInlining` (guarded devirtualization put it into `PropWriter<_, Vec3>.Write`: a frame of 184 bytes, set up per value; 10% of writing, arrays and maps). In shared generic code a cast to a type parameter is a generic dictionary lookup, so a target of a plan's own type goes through `Unsafe.As` (`PropWriter.Write`, `PropReader.Read`: write 5-9%, read 7%), and the root handler is kept by its root info (`WriteContext.RootHandlerOf`) instead of `as ValueHandler<T>` + `(T)value` (a state 134 -> 108 ns with generated code). `MsgPackWriter.Raw(byte[])` copies up to 16 bytes as two overlapping blocks (`Memmove` was 10% of writing names), `Single`, `Double` and `CompactUnsigned` load and store `Pos` once. All together, arrays without the schema, write on .NET 8: state 190 -> 163 ns, snapshot 2.29 -> 1.95 µs; generated 134 -> 108 ns, 1.46 -> 1.16 µs; generated names 260 -> 200 ns, 3.45 -> 2.6 µs. .NET 10 gains less: 172 -> 160 ns, 2.13 -> 1.93 µs; generated 115 -> 105 ns, 1.28 -> 1.21 µs; generated names 237 -> 195 ns, 3.09 -> 2.5 µs (in one process with all setups, `BenchmarkGame` is that: without generated code 180 -> 179 ns, 2.36 -> 2.26 µs, the shared profile). The invoices: names write 13% faster, generated names 10%, the rest the same; `double[]` write 3.65 -> 2.7 µs.
- Compiled writers (A/B on .NET 8, after the threshold): invoices write 4.42 -> 2.76 ms (default options), 4.01 -> 2.55 ms (arrays without the schema), 5.17 -> 4.18 ms (maps, indexed), 5.08 -> 4.05 ms (maps, names), the generated code's 2.74 / 2.44 / 3.63 / 3.56 ms (maps unrolled since; measured later, same machine); game writes 183 -> 113 ns per state, 2,259 -> 1,200 ns per snapshot (noschema), names 277 -> 223 ns / 3,803 -> 2,774 ns; allocations and reading unchanged. Compiling costs 1.2 ms for 3 properties and 6.5 ms for 25 (warm; the first in a process ~16 ms, loading the expression compiler), 90% of it the JIT (with `DOTNET_JITMinOpts=1` 0.6 ms for 25): `DynamicMethod.CreateDelegate` optimizes at once and inlines the writer's methods per property, hence the thread pool.
- Numbers on the wire are one store with `BinaryPrimitives` (byte by byte had a bounds check per byte, the JIT of .NET 8 does not merge them): `double[]` write 1.7x, read 2.2x; the invoices stay the same (few numbers of more than one byte). 
- `ObjectPlan.Write` stays as small as it is: whether guarded devirtualization inlines it into the loops of collections decides their speed. The generated code's unrolled maps are chosen in `GeneratedObjectCode<T>.WriteBoxed` (`UnrolledMap && keys != null`), not there: a branch more in `Write`, or a call with one argument less, made a dictionary of objects with compiled writers 7% slower (752 -> 794-812 ns, array layout, where the branch never runs).
- Keep the element loop inside `ListHandler.Write`/`ListReader.Read` (`ITypedElements`/`ICollectionContent` call those): in a method of its own, even `AggressiveInlining`, `ObjectPlan.Write` is no longer inlined into the loop by guarded devirtualization and generated code wrote the invoices 2-3% slower.
- `Buffer.BlockCopy` checks types (span copies for keys), `decimal != 0m` is a call (`DecimalHandler.IsZero`), `new T()` of a class is `Activator.CreateInstance` (compiled after 100 calls).
- Per call: the inline schema is recognized by comparing its bytes with the last one (`SchemaHit`), the published session's settings and binding are shared (`SessionShared`), the plans remember their last session binding / ids, `TypeResolver.CacheAssembly` checks lock-free first. The last root type's `FullPropertyInfo`, handler, `WriteTypeInfo` and reader are kept in the per-thread contexts (`WriteContext.RootInfo`/`RootHandler`/`RootTypeInfo`, `ReadContext.RootType`/`RootReader`; not in shared fields, which a server writing several root types would keep overwriting): the hash of a `Type` is a call into the runtime.
