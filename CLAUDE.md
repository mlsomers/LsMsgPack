# LsMsgPack

MsgPack serializer for .NET classes (like the xml and json serializers) with an optional indexed schema and type ids for polymorphic object models, plus a MsgPack explorer/debugging tool (Windows). The library is `LsMsgPackNetStandard/` (assembly and package `LsMsgPack`), on top of `LsMsgPackCore/` (assembly and package `LsMsgPack.Core`), which it shares with `LtMsgPack/` (a second serializer that writes and reads the same data without the item tree, see below). Not published as a NuGet package yet, so format changes are still acceptable when they are deliberate and called out.

## Build and test

```bash
dotnet build LsMsgPack.slnf -c DEBUG                  # what CI does (.github/workflows/dotnet.yml), cross-platform projects only
dotnet test LsMsgPack.slnf --no-build -c DEBUG
dotnet test LsMsgPackNetStandardUnitTests/LsMsgPackUnitTests.csproj -c Release --filter "TestCategory!=Benchmark"
dotnet test LsMsgPackNetStandardUnitTests/LsMsgPackUnitTests.csproj -c DebugKeepTrack --filter "TestCategory!=Benchmark"
dotnet test LsMsgPackInteropTests/LsMsgPackInteropTests.csproj -c Release
```

- `LsMsgPack.sln` also has Windows-only projects (MsgPackExplorer, Fiddler inspector, Visual Studio plugin: old-style .NET Framework projects). They reference the library project but cannot be built on Linux, mention it when a change could affect them (e.g. target frameworks, public API).
- Configurations: `Debug`, `Release`, `DebugKeepTrack`, `ReleaseKeepTrack`. KeepTrack defines `KEEPTRACK`: items remember offsets and lengths, errors become `MpError` items instead of exceptions (`ContinueProcessingOnBreakingError`), and `PreservePackages` keeps the item trees. The explorer tools use it. Code in `#if KEEPTRACK` blocks must keep compiling, so build a KeepTrack configuration after touching `MsgPackItem` or the `Types/`.
- `LsMsgPackInteropTests` checks what MessagePack-CSharp and Nerdbank.MessagePack read of LsMsgPack's output and the other way around (the invoice model with property names, byte equality per type, and the known differences: Guid, decimal, `DateTimeKind.Unspecified`, `DateTimeOffset`, polymorphism, omitted defaults, the indexed schema). A format change can make these fail: update the test when the change is intended, and mention it. `docs/Compatibility.md` documents the settings per library (from these tests), keep it in sync.
- **Shared tests**: the object-level test classes (`SerializingObjects`, `SerializingCollections`, `SerializingFrameworkTypes`, `SerializingGenericTypes`, `SerializingInheritanceHierarchy`, `SerializingPrimitives`, `SerializerRegressionTests`, `DeserializingEdgeCases`, `UnknownExtensions`, `CachedSchemaTests`, and in the interop project `MessagePackCSharpTests`, `NerdbankTests`) are abstract and call `Serializer` (an `ISerializerUnderTest`, `SerializerUnderTest.cs`, linked into the interop project); `Ls<Name>`/`Lt<Name>` subclasses at the end of each file run them against LsMsgPack and LtMsgPack. Call `Serializer.Serialize(...)`/`Serializer.Deserialize(...)` in them (extension methods mirror the overloads of `MsgPackSerializer`) and describe the settings with `MsgPackSettings`: the Lt adapter copies the format settings into `LtMsgPackOptions` (cached per combination of values) and maps custom extensions through `LtSerializer.ExtensionEquivalents` (decimal built in, the Nerdbank Guid added by the interop project; others make the Lt run inconclusive). Unknown extensions: `Serializer.IsUnknownExtension`. Item tests (`Mp*Test`, `MpRootTests`, `Extensions/`), `CompiledPropertyAccessors` and KEEPTRACK stay LsMsgPack-only.
- **Web formatters** (`LsMsgPackFormatters` ASP.NET Core, `LsMsgPackWebApiFormatters` Web API 2 + HttpClient, `LsMsgPackMvc` MVC 5 on .NET Framework) use **LtMsgPack**, not LsMsgPack (class and package names kept). They share `LtMsgPack/Http/`: `LtMsgPackHttpOptions` (`XLsMsgPack` for application/x-lsmsgpack, `Plain` for application/msgpack and x-msgpack, `NegotiateSchemas`) and `LtMsgPackHttpSerializer` (one per registration, input and output share it and its `SchemaStore`). Schema negotiation for x-lsmsgpack responses: request header `MsgPack-Schemas` (ids the client holds), response header `MsgPack-Schema` + `Vary`; the server writes with `WriteSchemaReference` and replaces the reference by the schema (`SchemaStore.GetInlineSchema`) when the client does not hold it or the schema is not longer than the reference. The client side is `LsMsgPackSchemaHandler` (`formatter.CreateHandler()`), which registers inline schemas (`SchemaStore.RegisterInline`) per server. Request bodies always carry the schema inline (by design, see `docs/WebFormatters.md`). The formatter test projects also reference LsMsgPack, to check the bytes against it. `LsMsgPackMvcTests` (net472) builds but cannot run on Linux.
- **Tests that inspect the map format** (keys, `MpMap` casts, expected lengths, resolving types by signature, settings for other libraries) set `ObjectLayout = ObjectLayout.Map`, the default writes arrays.
- The benchmark tests (`TestCategory=Benchmark`, `BenchmarkInvoices`) compare with System.Text.Json (the baseline, default options; also listed: its source generation and Json.NET) and report through `TestContext`: run them with `--logger "console;verbosity=detailed"`. They are Inconclusive under KEEPTRACK.
- **Two assemblies, same namespaces** (`LsMsgPack.*`). `LsMsgPack.Core` has what does not depend on `MsgPackItem`s: `MsgPackMediaTypes` (`ToPlain<T>` works for both libraries' settings), `MsgPackOptions` (the format settings, abstract; `MsgPackSettings` derives from it and adds custom extensions, the KEEPTRACK settings and buffers), `MsgPackTypeId`, `MsgPackException`, `Meta/` (`FullPropertyInfo`, `PropertyAccessor`, `TypeResolver`, `CollectionInfo`, `Instances`, `ByteWriter`, `NumericTypes`, `MapConversionEqualityComparer`, and the decisions both serializers share: `SerializationRules` for writing (type ids, collections), `ValueConverter` for converting unpacked values, `FrameworkTypeInfo`), all of `TypeResolving/` (interfaces, attributes, filters, resolvers, `IndexedSchemaTypeResolver`) and `Schema/`. `LsMsgPack` keeps the items (`MsgPackItem`, `Types/`), the serializer, `FrameworkTypes`, `MsgPackMeta`. Core's internals are visible to `LsMsgPack`, `LtMsgPack` and `LsMsgPackUnitTests`. Resolver and filter interfaces take `MsgPackOptions`. Core must not reference LsMsgPack: shared helpers live in Core and the old LsMsgPack members delegate (`MsgPackItem.SwapEndianChoice`, `MpString.DefaultEncoding` → `MsgPackOptions.StringEncoding`, `MsgPackMeta.NumericTypes`, the header writers in `ByteWriter`).
- The old-style Windows projects do not get transitive project references: they reference both `LsMsgPack.csproj` and `LsMsgPack.Core.csproj`.
- `MicroFramework/` has its own old copies of the sources, it does not link the library files.
- The version comes from `CommonAssemblyInfo.cs` (read by `Packaging.props`).

## Language and targets

- The library targets `netstandard2.0;netstandard2.1`. 2.1 only exists to ask `RuntimeFeature.IsDynamicCodeCompiled` (`#if NETSTANDARD2_1_OR_GREATER`), .NET Framework picks 2.0, .NET (Core) picks 2.1.
- netstandard2.0 compiles as **C# 7.3**: no `??=`, switch expressions, `is not`, ranges, `using` declarations or nullable annotations. `Dictionary.TryAdd` comes from `Meta/MissingExtensions.cs`.
- Style: 2-space indentation, `_camelCase` fields, explicit types rather than `var`, comments explain why. Some files use a different brace style, match the file. Most files are UTF-8 with BOM, keep it when editing with scripts (e.g. Python `encoding='utf-8-sig'`).

## How it works

- **Two phases.** Writing: object → `MsgPackItem` tree (`MsgPackSerilaizer_Pack.cs`, note the typo in the name: `SerializeObject`, `SerializeCollection`, `AddProperties`) → bytes (`MsgPackItem.WriteTo(ByteWriter)`, containers write their items into the same buffer). Reading: bytes → `MsgPackItem` tree (`MsgPackItem.Unpack`, each `Types/Mp*.Read`) → plain values (`object[]` for arrays, `KeyValuePair<object, object>[]` for maps) → objects (`MsgPackSerializer_Unpack.cs`: `ConvertDeserializeValue`, `ConvertMap`, `SetProperties`).
- **Items** (`Types/`): `MpInt` (keeps the original integer type, `DynamicallyCompact` picks the smallest encoding), `MpString`, `MpBin` (also `Guid`), `MpFloat`, `MpBool`, `MpNull`, `MpArray`, `MpMap`, `MpExt` → `MpDateTime` (type -1, timestamps) and custom extensions via `AbstractCustomExt<TSelf>` (`MpDecimal`, type 1, registered in `MsgPackSettings.CustomExtentionTypes`), `MpRoot` (several items in sequence), `MpError` (KEEPTRACK). Framework types without settable properties are written like MessagePack-CSharp does (`Meta/FrameworkTypes.cs`): `char` as an integer, `TimeSpan` and `TimeOnly` as ticks, `DateOnly` as its day number, `Uri` as its original string (`DateOnly`/`TimeOnly` are found by name, .NET Standard does not have them). Other types without settable properties still become an empty map.
- **Unknown extensions** (a type code without a registered custom extension) stay an `MpExt` in the unpacked tree (`MsgPackItem.UnpackedValue`, used by `MpArray`, `MpMap` and the serializer's root): they are converted to `byte[]` or kept as `MpExt` (object), anything else throws. Their bytes used to be converted like `bin` (a 16 byte extension became a Guid).
- **Objects** are arrays of their values by default (see the array layout below), or with `ObjectLayout.Map` maps from property id to value. The property id is the name, or what an `IMsgPackPropertyIdResolver` returns (`PropertyNameResolvers`), or with the indexed schema the index of the name in the schema. Filters: static ones decide per property (`FilterNonSettable`, `FilterIgnoredAttribute`, `FilterStatic`), dynamic ones per value (`FilterDefaultValues`: default values are omitted).
- **Array layout** (`MsgPackOptions.ObjectLayout.Array`, the default, writing only): an object is an array of its values in `PropertyOrder` (Ls `SerializeAsArray`, Lt `ObjectPlan.WriteArray`), nil for a value the dynamic filters leave out. Trailing nils are kept by default (the same bytes as MessagePack-CSharp's `[Key(n)]`, `IntegerKeys_SameBytesAsArrays`) and left out with `TrimTrailingNulls` (Lt reserves the array header and patches it, `MsgPackWriter.PatchArrayHeader`; nil is the only one byte value 0xC0). `MsgPackMediaTypes.ToPlain` and the `LtMsgPackPresets` for other libraries switch to `ObjectLayout.Map`. A type id wraps it: `{ "": typeId, "@": [values] }`; without a type id an ambiguous value throws (`SerializationRules.ThrowIfUnresolvableAsArray`). Readers take an array assigned to an object type by position (Core `ValueConverter.ConvertPositional`, Lt `ObjectReader.ReadPositional`): with the indexed schema the positions are matched by the names of the schema (the writer's order does not matter), without it the reader's own order must match the writer's. A nil or missing value leaves the property as the constructor made it (like a key that is not in a map), extra values are skipped. Known difference with maps (accepted, `ExplicitNullKeepsTheConstructorValue`): a null the filters keep (e.g. `[DefaultValue("Woof")]` with the value null) is read back as the constructor's value; an "explicit null" can be added when someone needs it. The ids are still resolved before the type id and the values, so the schema is the same as for maps.
- **Reserved map keys**: `""` holds the type id and `"@"` the content of a wrapped value (`MsgPackSerializer.TypeIdKey` / `ContentKey`). A collection is written as an array (a dictionary as a map), and only wrapped in a map when it needs a type id or properties (`SerializeEnumerableAttribute.SerializeProperties`).
- **Type ids** are added when the value's type differs from the declared type (`AddTypeIdOption.IfAmbiguious`, default). They are short type names by default (`AddTypeIdOption.FullName` for full names), and resolved again by name when reading (`Meta/TypeResolver.cs`).
- **Indexed schema** (`UseInexedSchema`, on by default): each `Serialize`/`Deserialize` call is a **session** with its own `IndexedSchemaTypeResolver` and a clone of the settings (`MsgPackSerializer.WithSchema`). The payload is a map `{ typeName: [propertyName, ...] }` followed by the body, in which property keys and type ids are indexes into that map. The resolver is both a type resolver and a property id resolver. Resolvers are consulted from **last to first**: the schema is added last to the type resolvers (asked first) and first to the property id resolvers (asked last, so custom property ids win). Readers look property ids up by name in the schema of the payload, so schema contents may change between versions.
- **Cached schema** (`SchemaStore`, `Schema/`): sessions kept between calls. Writing with `WriteSchemaReference` keeps one session per root type and settings (`SchemaStore.SessionKey`: type resolvers, static filters, property id resolvers, `AddTypeIdOptions`, `EndianAction`, `PropertyOrder`, arrays compared by reference) and writes `D8 02` + a 16 byte `SchemaId` (truncated SHA-256 over a format version byte and the schema packed in the specification's byte order) instead of the schema. Reading looks the id up in the store (`SchemaProvider` or `MissingSchemaException` when missing) or, with the schema inline, recognizes the schema by its bytes (`CacheInlineSchemas`); the inline format is unchanged. A published `SchemaSession` is **frozen** (shared by threads, `settings._schemaFrozen`, `IndexedSchemaTypeResolver.IsFrozen`): a call that needs a new type, property or cache entry gets the internal `SchemaGrowthException`, then repeats the work under the state's lock with a copy (`Thaw`) that is published in its place (writing: a new schema id, appended only, so older ids stay valid). `IndexedSchemaTypeResolver.Unpack` reads the schema from the bytes (`SchemaBytes`), without `MsgPackItem`s.
- **Resolving the properties of a type** (`FullPropertyInfo.GetSerializedProps`): in a session, `GetStaticallyIncludedProps` creates the properties once and runs the static filters (with `PropertyId` = name), then the ids are resolved for the kept ones. `IndexedSchemaTypeResolver.GetComplex` takes the names from the same list. Without a session (no schema) the old order is kept: the id is resolved first, then the static filters.
- **Property order** (`MsgPackOptions.PropertyOrder`, `FullPropertyInfo.GetProperties(Type, MsgPackOptions)`, decided once per type): `Reflection` (default, what `Type.GetProperties()` returns, the output so far), `Alphabetical` (ordinal), `Declaration` (base classes first, then by metadata token; an override keeps the position of the property it overrides), `Explicit` (`[DataMember(Order = n)]` first, then the others in declaration order), `TypeThenDeclaration` (by `PropertyType.ToString()`, which has no assembly names, then declaration order). It orders the map entries and the names in the schema; readers look properties up by name, so any order reads with any other. Both serializers get it through `GetSerializedProps`/`GetStaticallyIncludedProps`.

## LtMsgPack

`LtMsgPack/` (assembly and package `LtMsgPack`, references only `LsMsgPack.Core`): `LtMsgPackSerializer` (instance per `LtMsgPackOptions : MsgPackOptions`, the options are copied) writes the **same bytes** as LsMsgPack with the same settings and reads the same values, 4-7x faster than Json.NET on the invoices. `CrossLibraryTests` checks bytes and read values for a corpus in all settings (EndianAction × DynamicallyCompact × names/inline/reference): run it after changing either serializer.

- **Writing**: `IO/MsgPackWriter` has LsMsgPack's encodings (MpInt with and without DynamicallyCompact, MpString, MpBin, MpFloat, MpDateTime, MpExt). `Writing/`: a typed `ValueHandler<T>` per declared type (no boxing, typed getters via `Delegate.CreateDelegate`), `ObjectPlan` per type. A value of another runtime type goes through `Serializer.WriteBoxed`, which mirrors LsMsgPack's `SerializeObject`/`SerializeCollection`/`SerializeElements` (classification in `TypeKind`, in the order of `MsgPackItem.Pack`) and uses Core's `SerializationRules`. Property and type ids (`WriteContext`): names; `IdMode.Inline` builds the schema of the call in the same order as LsMsgPack's session (`InlineSchema`: a type is added when its property ids are resolved, if it has properties, or when its type id is written; the elements of a wrapped collection come before its type id, so they are written to a rented writer first); `IdMode.Session` uses a Core `SchemaSession` (schema references via `SchemaStore.RunWriter`, or per call with custom property id resolvers or custom dynamic filters).
- **Reading**: typed `ValueReader<T>` (`Reading/`) read the formats they expect and otherwise rewind to the start of the value and read it as LsMsgPack does: `MsgPackReader.ReadPlain` (what `MsgPackItem.UnpackedValue` returns) + Core's `ValueConverter`. `ObjectReader<T>` handles maps with the type id as first key and keys by name or schema index (`BoundSchema` binds the schema's property names to the local properties), and arrays (`ObjectLayout.Array`, also wrapped as `{ "": typeId, "@": [...] }`) by position; anything else (a type id elsewhere, `"@"`, custom resolvers) takes the LsMsgPack way. Schemas read inline are cached by their bytes (the options' `SchemaStore` or a private one), with Core's `SchemaStore.Entry.RunReader`.
- **Options of other libraries** (LtMsgPack only, the defaults write what LsMsgPack writes): `GuidFormat`, `DecimalFormat`, `DateTimeOffsetFormat`, `UnspecifiedDateTimeKind`, decided per type in `WriteTypeInfo` (kinds `GuidString`, `DecimalString`, `DateTimeOffsetArray`, no cost per value), and the built-in `NerdbankGuidExtension`. `LtMsgPackPresets` combines them for MessagePack-CSharp, Nerdbank.MessagePack and generic (Python, JS...) peers: `PresetTests` in the interop project checks them against those libraries' defaults (MessagePack-CSharp: the same bytes). Documented in `docs/Compatibility.md`.
- **Differences** (documented, by design): custom property id resolvers are asked once per type (plan) in names mode, not per call; duplicate map keys: the last one wins (LsMsgPack: the first); properties are set in the order of the data (LsMsgPack: last to first); unknown extensions become `MsgPackExtension` (LsMsgPack: `MpExt`); custom extensions derive from `LtExtension<T>` (not `ICustomExt`, which creates items); no KEEPTRACK.
- netstandard2.0 build: C# 7.3 like the library, `Span` from System.Memory, `Unsafe` from System.Runtime.CompilerServices.Unsafe.

## Caches and their scope

| Cache | Key | Scope |
|---|---|---|
| `FullPropertyInfo.Cache` | PropertyInfo | global, only without property id resolvers. `StaticallyIgnored` is cached on these shared instances, so the static filters of the first settings win |
| `FullPropertyInfo.SerializedPropsCache` | Type, one per `PropertyOrder` | global, only without property id resolvers and without a session (follows from the above) |
| `FullPropertyInfo.OrderedPropertiesCache` | Type, one per `PropertyOrder` (not `Reflection`) | global, static metadata |
| `FullPropertyInfo.AttributesCache`, `GetProperties` cache | PropertyInfo / Type | global, static metadata |
| `MsgPackOptions._serializedPropsCache`, `_staticPropsCache` | Type | one session (set by `WithSchema` or `SchemaSession.Apply`, not copied by `Clone()`/`CloneOptions()`). Property ids are schema indexes, never share them between sessions |
| `SchemaStore` schemas, inline schemas, writer and reader sessions | `SchemaId` / schema bytes / `SessionKey` | one store (shared by the settings that use it). Received schemas limited by `MaxSchemas`, sessions frozen once published |
| `PropertyAccessor.Cache` | PropertyInfo | global. Reflection for the first 100 calls, then typed delegates (`Delegate.CreateDelegate` into `TypedAccessor<TTarget, TValue>`), unless the runtime does not compile code or `MsgPackOptions.CompilePropertyAccessors` is off |
| `CollectionInfo`, `HasParameterlessConstructor`, `FilterDefaultValues.DefaultInstances` | Type | global |
| `TypeResolver` name caches | name / Type | global, guarded by one (re-entrant) lock |

Custom property id resolvers without the schema are consulted on every call (by design, they may have their own cache).

## Invariants and gotchas

- **Keep the output stable.** Performance changes must not change the bytes or the round trip results: verify with the `lsmsgpack-perf` skill (A/B equivalence and benchmark against master).
- **Leaf items write themselves** through `WriteTo` only when `GetType() == typeof(ThatType)`, because a subclass (e.g. a user's custom extension) may override `ToBytes`, which must still be used. `ToBytes` and `WriteTo` share one private writer per type, so they cannot drift apart.
- **Property ids must be unique per type** and must not be `""` or `"@"`: `FullPropertyInfo.ThrowIfIdsNotUnique` checks this once per type, the map entries are then collected in arrays without checks.
- **Exceptions of property getters/setters** are rethrown as they are (not as `TargetInvocationException`), whether the accessor still uses reflection or a bound delegate.
- The parameterless `MsgPackItem()` constructor allocates a new `MsgPackSettings` (50-70 ns). Use the constructors taking the settings in hot paths (see `AbstractCustomExt.CreateNew`).
- **Culture-sensitive string APIs are slow on Linux** (ICU): always pass `StringComparison.Ordinal` (`EndsWith`, `StartsWith`, `IndexOf(string)`, `Compare`).
- Reading from a `Stream`: use `ReadExactly` (`MsgPackItem`), `Stream.Read` may return fewer bytes than asked (network streams).
- Endianness: MsgPack is big-endian, `EndianAction` can override it. `ByteWriter.WriteEndian` writes the same bytes as `BitConverter.GetBytes` followed by `SwapEndianChoice`.
- `DateTime` values are returned as local time (`MpDateTime.Value` calls `ToLocalTime`), MsgPack timestamps do not keep the `DateTimeKind`: compare with `ToUniversalTime()` in tests. `DateTimeOffset` is written as its UTC time, the offset is lost. Timestamps before 1970 round the seconds down, the nanoseconds are always added (`MpDateTime.DateTimeToEpoch`), as the spec requires.
- Reading maps uses `MapConversionEqualityComparer`: numbers are equal across types (`(byte)3` equals the property id `(int)3`), strings and integers take a fast path.
- **Type injection** (docs/security.md): a type picked by the data (type id, schema name, custom resolver) must be assignable to the declared type, checked in `TypeResolver.Resolve` (Core, so both serializers) before the instance is created; names with `,` `[` `]` `&` `*` are refused in `TypeResolver.ResolveName` (`Type.GetType` would load the named assembly). The optional `MsgPackOptions.TypeGuard` (`IMsgPackTypeGuard`, `AllowedTypesGuard`) is asked only when the picked type differs from the declared one: in `TypeResolver.Resolve` and in LtMsgPack's `ObjectReader` fast path (which does not go through `Resolve`). A new place that creates instances of a type from the data must do the same checks (`TypeInjectionTests`).
- **Type names are short by default**, so the classes of an assembly that is searched for types need unique names: two test classes both called `Assorted` (nested in different test classes) make deserializing either of them throw "Type assignment dilamma". Give test classes unique names.
- `Deserialize<List<T>>` only registers the assembly of `List<T>`. When `T` lives elsewhere (and is not reachable from the root type), call `MsgPackSerializer.CacheAssemblyTypes(typeof(T))` (or `LtMsgPackSerializer.CacheAssemblyTypes`, the same cache) first. docs/schema.md (polymorphic class-hierarchy support) explains the lookup order to users.
- `Type.GetProperties()` without binding flags also returns **public static properties**: `FilterStatic` (in `Default_StaticFilters`) leaves them out, so the data cannot set shared state. Static filters set without it still serialize (and set) settable static properties.
- **`MsgPackOptions.MaxDepth`** (256, shared by both serializers): reading refuses arrays and maps nested deeper (LsMsgPack: `MsgPackItem.Unpack` passes the depth to `MpArray`/`MpMap.Read` via `_depth`, the exception is marked in `Exception.Data` so the levels above do not wrap it; under KEEPTRACK it becomes an `MpError`), writing refuses deeper objects and collections (cycles; LsMsgPack: the `depth` parameter of `SerializeObject`). Without it, deep data ended in a stack overflow, which ends the process.

## Performance

The baseline is **System.Text.Json** (default options, as ASP.NET Core uses it), since October 2026; Json.NET is about half as fast. Numbers from the `BenchmarkInvoices` test (100 invoices × 20 rounds, Release, i7-7700K, one run, speed relative to System.Text.Json; STJ source generation writes 1.33x and reads 1.0x):
- **LtMsgPack**: write 3.2x (indexed) / 3.2x (reference) / 2.8x (names), read 3.9x / 4.2x / 3.5x. `ObjectLayout.Array` (the default): write 3.5x (indexed) / 4.0x (reference) / 3.7x (no schema), read 4.2x. Payload 65-69% (indexed), 53-57% (reference), 95% (names). A single `Address` (per call cost): 0.18-0.19 µs write and 0.28 µs read (System.Text.Json 0.38 / 0.60 µs).
- **LsMsgPack**: write 0.26x (indexed) / 0.36x (reference) / 0.33x (names), read 0.37x / 0.51x / 0.43x (inline schema with a store 0.48x).
- End to end in ASP.NET Core (TestServer, one invoice per request): the msgpack formatters take ~21 µs per GET and ~34 µs per POST, System.Text.Json ~40 µs / ~52 µs. The framework is most of it.

What the LtMsgPack round of October 2026 found with `perf` (do not undo): `UTF8Encoding.GetBytes` costs 10-15 ns per call (strings up to 16 chars are written by a loop, longer ones in one pass with the header moved when needed), `Buffer.BlockCopy` checks types (span copies for keys), `decimal != 0m` is a call (`DecimalHandler.IsZero`), `new T()` of a class is `Activator.CreateInstance` (compiled after 100 calls), and per call: the inline schema is recognized by comparing its bytes with the last one (`SchemaHit`), the published session's settings and binding are shared (`SessionShared`, LtMsgPack does not change settings during a call), the plans remember their last session binding / ids, `TypeResolver.CacheAssembly` checks lock-free first. The formatters read the request body from the pipe in place (.NET 8).

Ideas not done yet:
- The remaining time of LsMsgPack is the `MsgPackItem` tree (building it, and converting it back to objects). LtMsgPack does without it.
- LtMsgPack reading: `DateTime` values cost ~4% in `ToLocalTime` (needed: LsMsgPack returns local time), strings ~12% in UTF-8 decoding. Writing: the virtual calls per property (`PropWriter` → `ValueHandler`).
- Reading: `ConvertMap` builds a dictionary per object to look up property ids, with the schema the keys are indexes that could address an array directly. Every value still becomes an `MsgPackItem` and then a boxed value.
- A source generator that writes (de)serializers at compile time (like System.Text.Json source generation / sgen.exe for xml).

Profiling on Linux: see the `lsmsgpack-perf` skill. `perf` works with `DOTNET_PerfMapEnabled=1` **and** `DOTNET_EnableWriteXorExecute=0` (otherwise the JIT code is double mapped and has no symbols), and needs `kernel.perf_event_paranoid` ≤ 1 (only the user can lower it). `dotnet-trace` stacks were unreliable.

## Working with the maintainer

- Create branches from `origin/master` with `--no-track` (`git switch --no-track -c <branch> origin/master`), then check `git status -sb` shows no upstream. With a tracking branch the maintainer's push landed on master.
- Commit, push and open pull requests only when asked. Commit messages: a short subject, a wrapped body explaining what and why, then the attribution line the harness provides.
- Report measured numbers (A/B, same session) and state behavior changes explicitly, the maintainer decides on format and behavior changes.
