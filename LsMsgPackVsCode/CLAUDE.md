# VS Code extension "MsgPack Explorer"

TypeScript, no bundler: the explorer of the Visual Studio visualizer for VS Code. Not published yet (publisher `mlsomers` in `package.json` is a placeholder for the marketplace id).

- `Server/` is `LsMsgPackInspector` (net8.0, in the slnf, run with the user's `dotnet`, published into `dist/inspector` by `npm run build:server`): JSON lines over stdin/stdout (`load`, `search`, `close`, `version`). `InspectorDocument` computes what the explorer control shows: tree within the display limit, offsets, type/length bytes for the hex colors (`typeBytes` 2 and `endBytes` 2 for a value of unknown length; kinds `index`, `tail`, `sidecar`), property grid values via `TypeDescriptor`, `MsgPackValidation` and `PayloadValidation` issues, objects via `RootObject` (see `../ObjectDebugger/CLAUDE.md`). It references the library with `AdditionalProperties="Configuration=$(KeepTrackConfiguration)"` (its own configuration when that is a KeepTrack one, otherwise `ReleaseKeepTrack`) and without the solution's properties, so it gets KEEPTRACK in any configuration (`SetConfiguration` is replaced in solution builds). The MCP server and its tests do the same.
- `src/debugBytes.ts` reads the bytes through DAP `evaluate` (C#: `byte[]`, streams with seek and restore, `IEnumerable<byte>`, `Memory<byte>`, HTTP content, strings, in base64 chunks that get smaller when the debugger shortens strings; also JavaScript and Python) or the `variables` of an array (any debugger). It, `inspectorClient.ts`, `bytesFromText.ts` and `mcpBridge.ts` do not import `vscode`, so `npm test` (node:test, `test/`) runs without VS Code (the inspector tests need `dotnet build LsMsgPackVsCode/Server`).
- `media/explorer.js` is the webview (virtual trees and hex view).
- MCP: `src/mcpBridge.ts` (the IDE bridge, see `../LsMsgPackMcpServer/CLAUDE.md`) + `src/mcp.ts` (registers the server with `registerMcpServerDefinitionProvider`, feature-detected). `test/mcpBridge.test.js` runs the .NET server against the TS bridge when built.
