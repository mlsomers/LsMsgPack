# Web formatters

`LsMsgPackFormatters` (ASP.NET Core), `LsMsgPackWebApiFormatters` (Web API 2 + HttpClient) and `LsMsgPackMvc` (MVC 5 on .NET Framework) use **LtMsgPack**, not LsMsgPack (class and package names kept). docs/WebFormatters.md. They share `LtMsgPack/Http/`:

- `LtMsgPackHttpOptions` (`XLsMsgPack` for application/x-lsmsgpack, `Plain` for application/msgpack and x-msgpack, `LtMsgPackPresets.Generic()` by default, `NegotiateSchemas`, `CompleteSchemas` and `PropertyNameCaseInsensitive`: on by default, set on both options' copies) and `LtMsgPackHttpSerializer` (one per registration, input and output share it and its `SchemaStore`).
- **Schema negotiation** for x-lsmsgpack responses: request header `MsgPack-Schemas` (ids the client holds), response header `MsgPack-Schema` + `Vary`; the server writes with `WriteSchemaReference` and replaces the reference by the schema (`SchemaStore.GetInlineSchema`) when the client does not hold it or the schema is not longer than the reference. The client side is `LsMsgPackSchemaHandler` (`formatter.CreateHandler()`; `CreateDelegatingHandler()` without an inner handler for IHttpClientFactory, which refuses handlers that have one), which registers inline schemas (`SchemaStore.RegisterInline`) per server; `RequestDescribedSchemas` (`CreateHandler(true)`) adds `x-lsmsgpack; schema=described` to the Accept header, for clients with other classes. Request bodies always carry the schema inline (by design, docs/WebFormatters.md).
- **Schema version 2 for clients without the classes** (`DescribeSchemas`, on by default, with the indexed schema, with or without negotiation): `Accept: application/x-lsmsgpack; schema=described` (`MsgPackMediaTypes.AcceptsDescribedSchema`, checked only for x-lsmsgpack responses) makes `LtMsgPackHttpSerializer` write with a second serializer (`SchemaVersion.Described`, the same `SchemaStore`: its schemas have their own ids and are negotiated alike), the body is the same; responses then have `Vary: Accept` (with `MsgPack-Schemas` when negotiated). Web API cannot set `Vary`: no workaround, the .NET readers read both versions.
- `ReportDifferences` (off by default, `LtMsgPackHttpSerializer.DeserializeBody`): ASP.NET Core `HttpContext.Features` + `ILogger` (Debug level, a warning with `LogDifferencesAsWarning`), Web API/HttpClient a `ConditionalWeakTable` per `HttpContent` (`GetReadDifferences()` on the content, request or response), MVC 5 `HttpContext.Items`; also the differences of a failed read (`DifferencesOf(ex)`).

## HttpClient helpers (LsMsgPackWebApiFormatters)

`MsgPackHttpClientExtensions` (docs/WebFormatters.md "HttpClient"), as System.Net.Http.Json: `GetFromMsgPackAsync` (ResponseHeadersRead, `MsgPackHttpException` for a status, disposes the response), `Post`/`Put`/`PatchAsMsgPackAsync` (`ObjectContent<T>` as x-lsmsgpack, status not checked), `EnsureSuccessStatusCodeAsync` on the response, `ReadFromMsgPackAsync` on `HttpContent` (`NotSupportedException` for another media type, with the start of a text body, or a stream; empty/204 = default, calls the formatter's `ReadFromStreamAsync`). `MsgPackHttpException : HttpRequestException` (docs/WebFormatters.md "Error responses"): ASP.NET Core sends problem details (application/problem+json) for status code results, `Problem()` and the automatic 400 whatever the Accept header (MVC limits them to the problem media types); it reads up to 64 KiB of the body, `Text` for text/JSON/XML, the problem members and `errors` with Newtonsoft (comes with WebApi.Client), `ReadBody<T>` for MsgPack. The package targets net8.0 too only to set the base `StatusCode` (no such constructor in .NET Standard; the netstandard builds have their own property). All send `Accept` only when neither the request nor `DefaultRequestHeaders` has one. The analyzers know these and the stream enumerables (`ModelTypes.FromInvocation`; the analyzer tests reference this package). Tests `HttpClientExtensionsTests`.

## HttpClient streams (LsMsgPackWebApiFormatters)

docs/WebFormatters.md "Streams with HttpClient". The package also targets netstandard2.1 for `IAsyncEnumerable` (`#if NETSTANDARD2_1_OR_GREATER || NET5_0_OR_GREATER`). `MsgPackStreamExtensions`: `StreamAccept` (as the TypeScript client's), `GetMsgPackStreamAsync`/`SendForMsgPackStreamAsync`/`ReadAsMsgPackStreamAsync` (ResponseHeadersRead, `MsgPackHttpException` for a status, `NotSupportedException` for another media type, 204/empty = an empty stream) return a reader from `LtMsgPackHttpSerializer.CreateStreamReader` (learns the head's schema with `LearnSchema` through `HeadSchemaRead`); `GetFromMsgPackAsAsyncEnumerable`/`ReadFromMsgPackAsAsyncEnumerable` (2.1) read `ReadHeadAsync<List<T>>` + `ReadElementsAsync`, so the payload of a `List<T>` of a server that doesn't stream reads the same (nil = none). `LsMsgPackSchemaHandler` does not buffer stream responses; the described range copies the parameters of the range it follows (`stream=unknown-length`). `MsgPackStreamContent` (request bodies, `CreateStreamWriter`: PerStream; `Create<T>(IAsyncEnumerable<T>)` writes the head of `List<T>`): no formatter reads such bodies, the server uses `CreateStreamReader`. Tests `StreamingClientTests` (TestServer drops what the client did not read yet when a response is aborted).

## ASP.NET Core (net8.0 parts)

- The output formatter, the input formatter and the minimal API types share `MsgPackResponse.WriteAsync` and `MsgPackRequest` (pipe reading in place, differences).
- **Minimal APIs** (docs/WebFormatters.md "Minimal APIs"): `services.AddLsMsgPack(...)` (`LsMsgPackFormatter.MinimalApis.cs`) registers an `LtMsgPackHttpSerializer` singleton (`TryAdd`, the `IOptions<LtMsgPackHttpOptions>` the MVC registration configures too); `MsgPackResult<T>` (`MsgPackResults.MsgPack(value)`, `Results.Extensions.MsgPack(value)`) negotiates by Accept like MVC (`MsgPackNegotiation`: quality then position, `*/*` = JSON as without `RespectBrowserAcceptHeader`; JSON through the minimal API `JsonOptions`' type info), declared type T (object: the value's class, as `ObjectResult`), always `Vary: Accept`; `MsgPackBody<T>` (`BindAsync`, `IBindableFromHttpContext`) reads MsgPack or JSON by Content-Type, null for empty/nil (ASP.NET Core then answers 400 for a required parameter; oblivious nullability = optional), `BadHttpRequestException` 400/415. Both add `Produces`/`Accepts` metadata. Tests `MinimalApiTests` (error status codes on Kestrel: TestServer passes exceptions to the client).
- **`IAsyncEnumerable<T>`**: `MsgPackResponse` reads it into a `List<T>` and writes that, when the declared type is `IAsyncEnumerable<T>`, or the value's class implements it and is not an `IEnumerable` (EF Core queries declared otherwise keep the synchronous enumeration); `MakeGenericMethod`, value types refused without dynamic code; lsmsgpack-ts maps such a result to `List<T>` (`SolutionRoots.Unwrap`) so the preloaded schema ids match.
- **Streaming responses** (docs/WebFormatters.md "Streaming responses"): with `stream=unknown-length` on the chosen media type in the Accept header (`MsgPackMediaTypes.StreamParameter`/`AcceptsStream`, `LtMsgPackHttpOptions.WriteStreams`) an `IAsyncEnumerable<T>` (not of pairs) is a head of `List<T>` (`LtMsgPackHttpSerializer.PrepareStreamHead` → `MsgPackStreamHead`, negotiated like a payload) + an array of unknown length, written by an asynchronous `MsgPackStreamWriter` to `Response.Body` (`MsgPackResponse.StreamAsync`: flushed when the next item is not there yet, after the first one, so an exception before it still gets an error response; no `DisposeAsync` after an exception); `MsgPackStreamResult` (MVC + `IResult`, `MsgPackResults.Stream`, `Results.Extensions.MsgPackStream`) hands an action an asynchronous writer (`CreateStreamWriter`, PerStream with references). Tests `StreamingResponseTests`.
- Trim/AOT: the net8.0 build runs the analyzers (`EnableTrimAnalyzer`/`EnableAotAnalyzer`, not `IsAotCompatible`: MVC is not trimmable) with context overloads of `AddLsMsgPackSerializerFormatters`. MVC 5 (net462) has no annotations.
